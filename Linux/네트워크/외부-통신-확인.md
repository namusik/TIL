# 외부 서버 연결 확인 (포트 · 서비스)

> 최종 업데이트: 2026-07-09 | Linux 기준

## 개념

"상대 서버에 연결이 되나?"를 확인할 때, **무엇을 확인하느냐**에 따라 도구가 갈린다. 크게 세 계층이다.

| 확인 대상 | 질문 | 대표 도구 |
|-----------|------|-----------|
| **호스트 도달** | 그 서버가 살아있나 | `ping` |
| **TCP 포트** | 그 포트가 열려 있나 | **`nc -zv`** · `telnet` · `/dev/tcp` |
| **서비스 응답** | HTTP가 실제로 응답하나 | **`curl`** |
| **경로** | 중간 어디서 막히나 | `traceroute` · `mtr` |

> 흔한 오해 — `ping`이 되면 "연결 OK"라고 생각하기 쉽지만, ping은 **포트를 확인하지 않는다.** 서버가 살아 있어도 원하는 포트(443 등)는 닫혀 있을 수 있고, 반대로 ICMP를 막아둔 서버는 **ping이 안 돼도 서비스는 멀쩡**하다. 포트 확인엔 `nc`를 쓴다.

도구별 요약이다.

| 도구 | 확인 대상 | 특징 |
|------|-----------|------|
| `ping` | 호스트 도달 | ICMP, 포트 무관 |
| **`nc -zv`** | TCP 포트 | 가볍고 빠름, **가장 추천** |
| `telnet` | TCP 포트 | 고전, 요즘 미설치 많음 |
| `curl` | HTTP 서비스 | L7 응답·상태코드·TLS까지 |
| `nmap` | 포트 + 서비스 | 상세 스캔 |
| `/dev/tcp` | TCP 포트 | 아무것도 없을 때 (bash 내장) |
| `traceroute`/`mtr` | 경로 | 어느 홉에서 막히는지 |

## ping — 호스트가 살아있나

```sh
ping -c 4 google.com
```
- ICMP로 호스트 **도달 가능 여부**만 확인한다. **포트는 확인하지 못한다.**
- `-c [횟수]`로 응답 없이 무한 반복되지 않게 지정한다.
- ⚠️ AWS 등 다수 서버는 보안상 **ICMP를 차단**한다. 이 경우 ping 실패가 곧 서비스 다운을 뜻하지 않는다 — 포트 확인으로 넘어간다.

## nc (Netcat) — 포트 확인 (추천)

```sh
nc -zv -w 5 google.com 443
nc -zv 142.250.206.110 443
nc -zv google.com 80 443 3306   # 여러 포트 한 번에
```
- telnet이 없는 최소 설치 환경에도 기본 포함된 경우가 많다.
- `-z`: 데이터를 보내지 않고 포트가 열려 있는지만 스캔
- `-v`: 자세한(verbose) 정보 출력
- `-w [초]`: 타임아웃 시간을 초 단위로 지정 (무한 대기 방지)
- 결과 해석:
  - 성공: `Connection to google.com 443 port [tcp/https] succeeded!`
  - 실패: `... failed: Connection refused` 또는 `timed out`

## telnet — 고전, nc 없을 때

```sh
telnet google.com 443
```
- 오래된 원격 접속 프로토콜이지만, 특정 서버·포트 연결 가능 여부를 간단히 확인하는 용도로 여전히 쓰인다.
- 결과 해석:
  - 성공: `Connected to google.com.` 표시 후 검은 화면에서 커서 깜박임 (종료: `Ctrl + ]` → `quit`)
  - 실패: `Connection refused`(포트 닫힘), `Connection timed out`(방화벽 등), `Unable to resolve host name`(도메인 문제)

## curl — HTTP 서비스까지 확인

포트 연결뿐 아니라 **실제 응답·상태코드·TLS 핸드셰이크**까지 본다.

```sh
curl -v https://google.com          # 연결~응답 전 과정
curl -I https://google.com          # 응답 헤더만 (상태코드 확인)
curl -v telnet://google.com:443     # 포트 연결만 점검 (telnet 없을 때)
```
- 웹 서버 포트(80/443)는 curl이 가장 유용하다 — 포트가 열렸어도 애플리케이션이 죽어 있으면 `nc`는 통과하지만 `curl`은 5xx/무응답으로 잡아낸다.
- 결과 해석:
  - 성공: `* Connected to google.com (...) port 443` + HTTP 응답
  - 실패: `Failed to connect ...: Connection refused` 또는 `Connection timed out`

## nmap (Network Mapper) — 상세 스캔

```sh
nmap -p 443 -sT google.com
```
- 포트 오픈 여부뿐 아니라 **어떤 서비스가 동작하는지, OS는 무엇인지**까지 얻을 수 있는 스캐닝 도구.
- 옵션:
  - `-p`: 특정 포트 지정 (`-p 80,443` / `-p 1-1000`)
  - `-sT`: 기본 TCP 연결 스캔
  - `-Pn`: 호스트 생존 확인(Ping)을 생략 — **ICMP가 차단된 경우 유용**
- 결과 해석:
  - 열림: `443/tcp open  https`
  - 실패: `closed`(닫힘) 또는 `filtered`(방화벽 등으로 확인 불가)

> `filtered`가 뜨면 방화벽이 패킷을 조용히 버리는 것으로, `nc`/`curl`의 `timed out`과 같은 상황이다.

## bash /dev/tcp — 아무것도 없을 때

```sh
echo > /dev/tcp/HOST/PORT
echo $?
```
- Bash 셸 **내장 기능**이라 nc·telnet 등 별도 유틸이 없어도 포트 연결을 확인할 수 있다.
- 동작 원리:
  - `/dev/tcp/HOST/PORT`는 실제 장치 파일이 아니라 **Bash가 특별하게 해석하는 가상 경로**다. 여기에 쓰기를 시도하면(`>`) Bash가 해당 HOST·PORT로 **TCP 소켓 연결을 시도**한다.
  - `echo $?`로 직전 명령의 **종료 코드**를 확인한다.
    - `0`: 연결 성공 (포트 열림)
    - `0 이외`(보통 1): 실패 — 호스트 없음/방화벽 차단/포트 닫힘
- 무한 대기를 막으려면 `timeout`과 함께 쓴다:
```sh
timeout 3 bash -c 'echo > /dev/tcp/google.com/443' && echo OPEN || echo CLOSED
```

## traceroute / mtr — 경로 어디서 막히나

연결이 안 될 때 **중간 어느 구간에서 끊기는지** 추적한다.

```sh
traceroute google.com          # 홉(라우터)별 경로 출력
mtr google.com                 # traceroute + ping 실시간 통계 (설치 필요)
```
- 목적지까지의 라우터(홉)를 순서대로 보여준다. 특정 홉부터 `* * *`만 나오면 그 지점(방화벽·게이트웨이 등)에서 막혔을 가능성이 높다.
- `mtr`은 경로별 패킷 손실률·지연을 실시간으로 보여줘 구간 장애 진단에 강하다.

## 에러 메시지로 원인 구분 (핵심)

연결 실패 시 **에러 종류가 원인을 알려준다.** 이 구분이 트러블슈팅의 절반이다.

| 결과 | 의미 | 원인·조치 |
|------|------|-----------|
| `succeeded` / `Connected` | 포트 열림 ✅ | 정상 |
| **`Connection refused`** | 도달은 했으나 그 포트에 **서비스 없음/다운** | 네트워크 경로는 뚫림. **서버 쪽** 프로세스·포트 확인 |
| **`Connection timed out`** / 무한 대기 | 응답 자체가 없음 | **방화벽·보안그룹이 조용히 DROP.** 대역·규칙 확인 |
| `Could not resolve host` | 이름 → IP 변환 실패 | **DNS** 문제. `/etc/resolv.conf`, 도메인 오타 확인 |

핵심은 **refused와 timeout의 차이**다.
- **refused** → 패킷이 상대에 **도달**했고, 상대가 "그 포트 안 열려 있다"고 **명시적으로 거절(RST)**한 것. 방화벽은 통과했으니 서버 설정을 본다.
- **timeout** → 응답이 아예 없다. 중간 **방화벽/보안그룹이 패킷을 말없이 버리는(DROP)** 전형적 증상이다. AWS 보안그룹은 거부 시 응답 없이 드롭하므로 항상 timeout으로 나타난다. (→ [방화벽](../../CS-이론/네트워크/방화벽.md))

## 결론 — 도구 선택 가이드

- **빠른 포트 확인**: `nc -zv host port` (telnet 대체, 기본 설치 확률 높음)
- **HTTP 서비스 확인**: `curl -v` / `curl -I` — 포트 너머 실제 응답까지
- **아무 도구도 없을 때**: `timeout 3 bash -c 'echo > /dev/tcp/host/port'`
- **상세 정보·다중 포트**: `nmap`
- **구간 장애 추적**: `traceroute` / `mtr`
- 실패하면 **에러 메시지부터** 보라 — `refused`(서버 문제) vs `timeout`(방화벽 DROP) vs `resolve`(DNS).
