# tcpdump — 패킷 캡처와 분석

> 최종 업데이트: 2026-06-17 | tcpdump 4.99 / libpcap 기준

## 개념

**tcpdump**는 네트워크 인터페이스를 지나가는 **패킷을 그대로 떠서 보여주는** 명령줄 도구다. "서버가 요청을 받긴 했나?", "연결이 어디서 끊겼나?", "누가 이 포트로 들어오나?"처럼 **애플리케이션 로그만으로는 안 보이는 네트워크 계층의 진실**을 직접 눈으로 확인할 때 쓴다.

> 비유: 우체국 컨베이어 벨트 옆에 서서 지나가는 우편물을 들여다보는 것. 보내는 주소(출발 IP)·받는 주소(목적 IP)·소인(포트·플래그)을 읽고, 필요하면 봉투를 열어 내용물(페이로드)까지 본다. 단, 봉인된 편지(TLS 암호화)는 겉봉투만 보이고 속은 못 읽는다.

서버 개발자에게 tcpdump는 **"애플리케이션 탓이냐 네트워크 탓이냐"를 가르는 도구**다. 중계사·외부 API 연동(예: SMPP TCP 세션)이 말없이 끊기거나 응답이 없을 때, 패킷이 실제로 오갔는지 확인하면 책임 소재가 명확해진다.

## 배경/역사

| 시기 | 내용 |
|------|------|
| 1988 | 미국 **Lawrence Berkeley Laboratory(LBL)** 의 Van Jacobson, Craig Leres, Steven McCanne가 개발 |
| 1992 | 패킷 필터링 엔진 **BPF(Berkeley Packet Filter)** 논문 발표 — 커널에서 효율적으로 필터링하는 구조 |
| 1999~ | 캡처 기능이 **libpcap** 라이브러리로 분리. tcpdump는 libpcap 위에서 동작 |
| 현재 | **tcpdump.org**(The Tcpdump Group)가 tcpdump·libpcap을 함께 유지보수 |

핵심은 tcpdump가 **libpcap**이라는 패킷 캡처 라이브러리 위에 얹힌 프런트엔드라는 점이다. 같은 libpcap을 Wireshark·tshark도 쓴다. 그래서 tcpdump로 뜬 파일을 Wireshark로 그대로 열 수 있다.

### BPF — 커널에서 거르고 올린다

tcpdump가 빠른 이유는 **필터링을 커널 안의 BPF가 처리**하기 때문이다. 우리가 준 필터 표현식(`port 8080` 등)을 BPF 바이트코드로 컴파일해 커널에 심고, **조건에 맞는 패킷만 유저 공간으로 복사**한다. 모든 패킷을 유저 공간으로 올린 뒤 거르는 게 아니라, 올라오기 전에 걸러 **부하를 크게 줄인다.**

## 기본 사용법

tcpdump는 패킷을 가로채야 하므로 **root 권한(sudo)** 이 필요하다.

```sh
sudo tcpdump                    # 기본 인터페이스에서 캡처 (이름 해석 때문에 느림)
sudo tcpdump -i eth0            # 특정 인터페이스 지정
sudo tcpdump -i any            # 모든 인터페이스
sudo tcpdump -D                # 캡처 가능한 인터페이스 목록 보기
```

가장 자주 쓰는 형태는 **이름 해석을 끄고(`-nn`) 개수를 제한**하는 것이다.

```sh
sudo tcpdump -i any -nn -c 20 port 8080
```

| 옵션 | 의미 |
|------|------|
| `-i` | 캡처할 인터페이스 (`any`=전체) |
| `-n` | IP를 **DNS로 역해석하지 않음** (호스트명 조회 지연·왜곡 방지) |
| `-nn` | IP·**포트 둘 다** 숫자 그대로 (예: `https` 대신 `443`) |
| `-c N` | N개만 잡고 종료 (운영 서버에서 필수) |
| `-v`/`-vv`/`-vvv` | 상세도 증가 (TTL·체크섬 등) |
| `-t`/`-tttt` | 타임스탬프 끄기 / 사람이 읽는 날짜시각 |
| `-e` | 이더넷(MAC) 헤더까지 표시 |

> 실무 팁: `-n`을 안 붙이면 tcpdump가 IP마다 역DNS를 조회하느라 느려지고, 그 조회 트래픽이 캡처에 섞인다. **운영 서버에서는 `-nn`을 기본**으로 깐다.

## 출력 한 줄 읽는 법

```
15:04:05.123456 IP 10.0.1.5.54321 > 10.0.2.7.8080: Flags [S], seq 12345, win 64240, length 0
```

이 한 줄을 앞에서부터 끊어 읽으면 다음과 같다.

| 토큰 | 의미 |
|------|------|
| `15:04:05.123456` | 타임스탬프 |
| `IP` | 프로토콜 (IPv4) |
| `10.0.1.5.54321` | **출발** IP·포트 (IP 뒤 마지막 숫자가 포트) |
| `>` | 방향 (출발 → 목적) |
| `10.0.2.7.8080` | **목적지** IP·포트 |
| `Flags [S]` | TCP 플래그 (`[S]`=SYN) |
| `seq 12345` | 시퀀스 번호 |
| `win 64240` | TCP 윈도우 크기 |
| `length 0` | 페이로드 바이트 수 |

TCP 플래그만 읽을 줄 알아도 연결 진단의 절반은 끝난다.

| 플래그 표기 | 의미 | 신호 |
|------------|------|------|
| `[S]` | SYN | 연결 시작 요청 |
| `[S.]` | SYN+ACK | 서버가 연결 수락 |
| `[.]` | ACK | 정상 데이터 주고받음 |
| `[P.]` | PUSH+ACK | 데이터 전송 |
| `[F.]` | FIN | 정상 종료 |
| `[R]` / `[R.]` | RST | **비정상 강제 끊김** (방화벽 차단·포트 닫힘·앱 비정상 종료 의심) |

> 예: SYN은 나가는데 SYN+ACK가 안 돌아오면 → 상대 포트가 닫혔거나 방화벽이 막은 것. RST가 바로 오면 → 상대가 연결을 거부한 것.

## 필터 (BPF 표현식)

tcpdump의 진짜 힘은 필터다. 명령 끝에 조건을 붙이면 해당 패킷만 잡는다.

### 호스트·포트·프로토콜

```sh
sudo tcpdump -nn host 10.0.2.7              # 이 IP가 출발 또는 목적지
sudo tcpdump -nn src host 10.0.2.7          # 출발지가 이 IP
sudo tcpdump -nn dst host 10.0.2.7          # 목적지가 이 IP
sudo tcpdump -nn port 8080                  # 출발/목적 포트 8080
sudo tcpdump -nn dst port 2775              # 목적 포트 2775 (SMPP)
sudo tcpdump -nn portrange 8000-8100        # 포트 범위
sudo tcpdump -nn net 10.0.2.0/24            # 특정 네트워크 대역
sudo tcpdump -nn tcp                         # TCP만 (udp / icmp 도 가능)
```

### 논리 조합 (and / or / not)

```sh
# 특정 호스트와 8080 포트 트래픽만
sudo tcpdump -nn host 10.0.2.7 and port 8080

# 8080이면서 SSH(22)는 제외
sudo tcpdump -nn 'port 8080 and not port 22'

# 두 후보 서버 중 하나라도
sudo tcpdump -nn 'host 10.0.2.7 or host 10.0.2.8'
```

> 복잡한 필터는 셸이 `(`, `)` 등을 해석하지 못하게 **작은따옴표로 감싼다.**

| 필터 키워드 | 의미 |
|------------|------|
| `host` / `src host` / `dst host` | IP 주소 |
| `port` / `src port` / `dst port` | 포트 |
| `portrange A-B` | 포트 범위 |
| `net` | 네트워크 대역(CIDR) |
| `tcp` / `udp` / `icmp` | 프로토콜 |
| `and` / `or` / `not` | 논리 결합 |

### 플래그로 거르는 고급 필터

```sh
# SYN 패킷만 — 새 연결 시도 추적 (커넥션 폭주 진단)
sudo tcpdump -nn 'tcp[tcpflags] & tcp-syn != 0'

# RST 패킷만 — 강제 끊김 추적
sudo tcpdump -nn 'tcp[tcpflags] & tcp-rst != 0'

# SYN 또는 FIN — 연결 시작/종료만
sudo tcpdump -nn 'tcp[tcpflags] & (tcp-syn|tcp-fin) != 0'
```

## 페이로드 내용 보기

헤더뿐 아니라 **실제 주고받은 데이터(평문)** 를 봐야 할 때가 있다.

```sh
sudo tcpdump -nn -A port 8080        # 페이로드를 ASCII로 (HTTP 등 텍스트 프로토콜)
sudo tcpdump -nn -X port 8080        # 16진수 + ASCII 병기 (바이너리 프로토콜 분석)
```

- **`-A`**: HTTP 헤더·평문 메시지 확인에 유용
- **`-X`**: SMPP 같은 **바이너리 PDU**를 바이트 단위로 뜯어볼 때 ([SMS PDU](../../CS-이론/네트워크/이동통신/SMS-기술규격.md)처럼 직렬화된 바이트 구조 확인)
- ⚠️ **TLS/HTTPS는 암호화돼 있어** `-A`로 봐도 의미 있는 평문이 안 나온다. 봉인된 편지의 겉봉투만 보이는 셈

## 파일로 저장하고 Wireshark로 분석

운영 서버에서 화면으로 분석하는 건 비효율적이다. **파일로 떠서(`-w`) 로컬 Wireshark로 분석**하는 게 정석이다.

```sh
# .pcap 파일로 저장 (화면 출력 없이 디스크에 기록)
sudo tcpdump -i any -nn -w capture.pcap port 8080

# 저장한 파일 다시 읽기 (필터도 적용 가능)
tcpdump -nn -r capture.pcap 'tcp[tcpflags] & tcp-rst != 0'
```

| 옵션 | 의미 |
|------|------|
| `-w 파일` | 패킷을 **pcap 파일로 저장** (원본 그대로, 분석은 나중에) |
| `-r 파일` | 저장한 pcap 파일을 읽어 분석 |
| `-s N` | snaplen — 패킷당 캡처할 바이트 수 (최신 기본값은 262144=전체) |

> 흐름: **서버에서 `-w`로 캡처 → scp로 내려받기 → Wireshark로 열기.** Wireshark가 같은 libpcap 포맷을 쓰므로 그대로 열리고, TCP 스트림 추적·통계 등 시각적 분석이 가능하다.

### 장시간 캡처는 링 버퍼로

오래 캡처하면 파일이 무한정 커져 **디스크가 찬다**( [리눅스 저장 공간](../시스템-리소스/리눅스-저장공간.md) 참고). 파일을 잘라 돌려쓰는 링 버퍼를 쓴다.

```sh
# 100MB마다 새 파일, 최대 10개만 유지하며 순환 (오래된 것 자동 삭제)
sudo tcpdump -i any -nn -w cap_%Y%m%d_%H%M%S.pcap -C 100 -W 10 port 8080
```

- **`-C N`**: 파일이 N(MB)을 넘으면 다음 파일로 / **`-W N`**: 파일 최대 N개로 순환 / **`-G N`**: N초마다 파일 교체

## 운영 서버에서 쓸 때 주의

tcpdump는 강력한 만큼 운영 환경에서 조심해야 한다.

- **성능 부하**: 필터 없이 고트래픽 서버에서 캡처하면 CPU·디스크에 부담. 반드시 **필터를 좁히고(`host`/`port`) `-c`나 `-C/-W`로 양을 제한**한다
- **보안·프라이버시**: 페이로드에 평문 비밀번호·개인정보·문자 본문이 그대로 찍힐 수 있다. pcap 파일은 **민감 정보 취급**하고, 분석 후 삭제한다
- **권한**: root가 필요하므로 함부로 남에게 열어주지 않는다
- **암호화 구간**: TLS 안의 내용은 못 본다. 평문이 필요하면 TLS 종단(로드밸런서 안쪽 등)에서 떠야 한다

## 정리

- **tcpdump** = libpcap 기반 패킷 캡처 도구. "앱 문제냐 네트워크 문제냐"를 가르는 진단의 핵심
- **BPF**가 커널에서 필터링해 매칭 패킷만 올리므로 효율적
- 기본기: **`-nn`(이름해석 끄기) + 필터(`host`/`port`) + `-c`(개수 제한)**
- **TCP 플래그(S/S./ ./R)** 만 읽어도 연결 진단의 절반
- 정석 분석: **`-w`로 pcap 저장 → Wireshark로 분석**
- 운영에선 **필터 좁히고·양 제한하고·민감정보 주의**
