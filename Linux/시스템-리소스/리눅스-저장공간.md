# 리눅스 저장 공간 관리

> 최종 업데이트: 2026-06-17 | EC2(Amazon Linux) · ext4 기준

## 개념

리눅스 저장 공간 관리는 **디스크가 왜 찼는지 찾아내고, 안전하게 공간을 회수하는 일**이다. 핵심은 리눅스가 파일을 "이름"과 "실제 데이터"로 나눠 다루기 때문에, **"지웠는데 용량이 안 줄어드는"** 현상이 자주 생긴다는 점이다. 이 동작 원리를 알아야 디스크 풀(full) 장애를 제대로 잡는다.

> 비유: 도서관에서 책(데이터)과 색인 카드(이름)가 따로 관리되는 것과 같다. 색인 카드를 버려도(rm), 누군가 그 책을 펼쳐 읽고 있으면(프로세스가 사용 중) 책 자체는 서가에서 안 치워진다. 그래서 "카드는 없앴는데 서가는 그대로"인 상황이 생긴다.

이 문서는 **현황 파악(df) → 범인 찾기(du) → 안전한 회수(truncate/logrotate)** 순서로, 디스크 풀 장애 대응에 필요한 도구를 정리한다.

## 디스크 동작 철학 — 파일과 이름의 분리

리눅스에서는 파일의 '이름'과 '실제 데이터(알맹이)'가 **별도로 관리**된다. 이 분리가 모든 용량 회수 이슈의 뿌리다.

| 구성 요소 | 역할 |
|----------|------|
| **알맹이 (Inode)** | 파일의 실제 데이터·소유자·권한 등 모든 정보가 담긴 본체 |
| **이름표 (Dentry)** | `ls`로 보는 파일 이름. 특정 Inode를 가리키는 포인터 |

- 하나의 알맹이(Inode)에 여러 개의 이름표를 붙일 수도 있다 → **하드 링크** ([파일-관리-명령어.md](../파일/파일-관리-명령어.md)의 `ln` 참고)

### rm 명령어의 실제 동작

`rm`은 파일을 직접 지우는 게 아니라 **이름표를 떼어내는(unlink)** 동작이다.

- 운영체제는 ① 알맹이를 가리키는 이름표가 모두 사라지고(참조 수 0) ② 그 알맹이를 사용 중인 프로세스도 없을 때, 비로소 "아무도 안 쓰니 버려도 되겠다" 판단하고 **디스크 공간을 회수**한다.

### 장점이자 단점

| | 내용 |
|---|------|
| **장점 (안정성)** | 어떤 프로세스가 파일을 사용 중인데 다른 사용자가 `rm`해도, 실행 중인 프로세스는 문제없이 작업을 계속한다. 시스템이 안정적으로 동작 |
| **단점 (오해)** | 사용자는 파일을 지웠다고 생각하는데 **디스크 용량은 줄지 않는** 현상 발생. 로그처럼 장시간 열려 있는 파일을 올바른 방법(프로세스 재시작 또는 `truncate`)으로 처리하지 않으면 생긴다 |

## /proc — 디스크를 쓰지 않는 가상 파일시스템

- `/proc`은 실제 디스크에 존재하는 '진짜' 파일시스템이 **아니다.**
- 커널이 메모리에서 관리하는 시스템 정보·프로세스 상태를 **파일 형태로 보여주는 '가상' 파일시스템(Virtual Filesystem)** 이다.

> 비유: 자동차 계기판. 계기판은 엔진이나 연료 탱크 자체가 아니지만, 현재 RPM·연료량 같은 실시간 정보를 보여준다. 마찬가지로 `/proc`은 커널 자체가 아니지만, 실행 중인 프로세스 목록·CPU 정보(`cat /proc/cpuinfo`)·메모리 상태(`cat /proc/meminfo`)를 파일처럼 보여주는 통로다.

- 접근할 때마다 커널이 즉석에서 정보를 만들어 보여주며, **디스크 공간을 차지하지 않는다.**
- 뒤의 "좀비 파일 해결 — /proc 비상 통로"에서 이 특성을 실제로 활용한다.

## df — 파일시스템 현황 파악

`df -h`로 어느 파티션이 찼는지부터 본다. (`-h`: 사람이 읽기 쉬운 단위 G/M/K로 표시)

```sh
[ec2-user@ip-10-0-137-112 log]$ df -h
Filesystem      Size  Used Avail Use% Mounted on
devtmpfs        3.9G     0  3.9G   0% /dev
tmpfs           3.9G     0  3.9G   0% /dev/shm
tmpfs           3.9G  395M  3.5G  11% /run
tmpfs           3.9G     0  3.9G   0% /sys/fs/cgroup
/dev/nvme0n1p1  8.0G  8.0G   20K 100% /
/dev/nvme1n1    1.0T   27G  998G   3% /data
tmpfs           785M     0  785M   0% /run/user/1000
tmpfs           785M     0  785M   0% /run/user/0
```

여기서 `/`(루트)가 **100%로 꽉 찬 상태**다. 이게 장애 지점이다.

### Filesystem 종류 읽기 — tmpfs는 디스크가 아니다

df 출력의 **절반이 tmpfs/devtmpfs**라 처음 보면 혼란스럽다. 이들은 **디스크가 아니라 메모리(RAM) 기반** 파일시스템이라, 실제 디스크 용량 분석에서는 **무시**하면 된다.

| Filesystem | 정체 | 디스크 차지? |
|-----------|------|-------------|
| **devtmpfs** | 커널이 만드는 장치 파일(`/dev`)용 가상 FS | ❌ (RAM) |
| **tmpfs** | RAM 기반 임시 FS (`/run`, `/dev/shm`, 사용자 세션 등) | ❌ (RAM) |
| **/dev/nvme0n1p1** | 실제 EBS 디스크 파티션 (루트 `/`) | ✅ |
| **/dev/nvme1n1** | 실제 EBS 디스크 (데이터 `/data`) | ✅ |

> 디스크 용량 장애를 볼 때는 **`/dev/...`로 시작하는 실제 블록 장치 줄만** 보면 된다. tmpfs가 꽉 차는 건 디스크가 아니라 메모리 이슈다.

### EBS 블록 장치 이름 읽기 (/dev/nvme...)

EC2에서 디스크는 NVMe 장치로 잡힌다.

| 이름 | 의미 |
|------|------|
| **nvme0n1** | 첫 번째 NVMe(EBS) 볼륨 |
| **p1** | 그 디스크의 첫 번째 **파티션** (`nvme0n1p1`) |
| **nvme1n1** | 두 번째 NVMe(EBS) 볼륨 (파티션 없이 통째 사용) |

- **`/dev/nvme0n1p1`**: 보통 루트(`/`)로 마운트. OS·시스템 파일이 저장되며, **100%가 되면 시스템 성능·안정성에 문제**가 생긴다
- **`/dev/nvme1n1`**: 용량이 크고 사용량이 적어 데이터 저장용(`/data`)으로 많이 쓴다

### 루트(/)가 찼을 때 우선 정리 대상

```sh
# 로그 정리 — 주로 /var/log
sudo du -sh /var/log/*

# 임시 파일 정리
sudo rm -rf /tmp/* /var/tmp/*          # 사용 중이지 않은 것만

# 패키지 매니저 캐시 정리
sudo yum clean all                      # RHEL/Amazon Linux
sudo apt clean                          # Ubuntu/Debian
```

## du — 용량 잡아먹는 범인 찾기

df로 "어느 파티션"인지 봤다면, du로 "그 안의 어느 디렉토리/파일"인지 좁힌다.

> 비유: df가 "몇 동이 꽉 찼나"라면, du는 "그 동의 몇 호가 짐을 쌓아뒀나"를 찾는 것.

```sh
# 현재 위치에서 1단계 깊이 디렉토리별 용량, 큰 순 정렬
du -h --max-depth=1 | sort -hr
```

- **`du`**: 디스크 사용량 표시 / **`-h`**: G·M·K 단위 / **`--max-depth=1`**: 1단계 깊이까지만(없으면 모든 하위까지 쏟아져 복잡)
- **`sort -h`**: G·M·K 단위를 숫자로 인식해 정렬(human-numeric) / **`-r`**: 역순(큰 것이 위로)

```sh
# 하위 디렉토리 제외, 바로 아래 파일들의 크기만 정렬
ls -lhrS
```

- **`-l`** 상세 목록 / **`-h`** 읽기 쉬운 단위 / **`-S`** 크기순 정렬 / **`-r`** 역순(내림차순)

```sh
# 큰 디렉토리를 위에서부터 한 줄로 빠르게
sudo du -sh * | sort -hr
```

> 참고: `du`가 너무 느리거나 대화형으로 탐색하고 싶으면 **`ncdu`**(별도 설치)가 편하다. 디렉토리를 들어가며 용량을 시각적으로 훑을 수 있다.

## 파일 삭제와 용량 회수

### ① 삭제 전 — 프로세스가 파일을 사용 중인지 확인

큰 파일(특히 로그)을 지우기 전, **누가 열고 있는지** 먼저 확인해야 한다. 이걸 건너뛰면 좀비 파일이 생긴다.

```sh
# 특정 파일을 사용 중인 프로세스 확인
lsof /var/log/app.log
```

- **결과가 출력됨** → 프로세스가 파일을 열고 있음 → `rm` 대신 **`truncate -s 0`** 을 쓰거나 프로세스 재시작
- **결과 없음** → 아무도 안 씀 → `rm`으로 삭제하면 즉시 용량 반환

```sh
# fuser로도 확인 (사용 중인 프로세스 PID만 간단히)
fuser /var/log/app.log
fuser -v /var/log/app.log    # 자세히
```

### ② 일반적인 삭제 (아무도 사용하지 않는 파일)

```sh
rm [파일명]        # 기본 삭제
rm -f [파일명]     # 묻지 않고 강제 삭제
```

- `rm`은 파일을 실제로 지우는 게 아니라 **이름과 inode의 연결을 끊는(unlink)** 작업
- 아무 프로세스도 사용 중이 아니면 → inode 참조 수 0 → **즉시 디스크 공간 반환**
- 이 경우 `df -h` 기준 용량이 바로 감소하고, 물리적으로도 공간이 확보된다

### ③ 지웠는데 용량이 안 줄어드는 케이스 — 좀비 파일

프로세스가 **사용 중인 파일을 `rm`** 하면 발생한다.

- 겉보기엔 파일이 사라졌지만, 디스크 용량은 그대로 차지하는 **'삭제 대기' 상태**(lsof에 `(deleted)`로 표시)
- 프로세스는 파일 디스크립터(FD)로 inode에 직접 연결돼 있어, **이름표가 사라져도 데이터를 계속 기록**한다. 오히려 로그가 더 쌓여 용량이 늘 수도 있다
- 그 파일을 연 **프로세스가 종료될 때 비로소 용량이 반환**된다

```sh
# 좀비(삭제 대기) 파일 확인 — (deleted) 표시된 것만, 큰 순으로
sudo lsof | grep deleted | sort -k 7 -n
```

- **`sort -k 7 -n`**: 7번째 컬럼(파일 크기) 기준 숫자 정렬 → 용량 큰 순

#### 해결 1 — 프로세스 재시작 (Best)

해당 프로세스를 재시작하면 붙잡고 있던 `(deleted)` 파일과의 연결이 끊겨 **디스크 공간이 완전히 회수**된다.

#### 해결 2 — 재시작 불가 시: /proc 비상 통로

서비스를 못 멈추는 상황이면, 앞서 본 `/proc`의 특성을 이용한다.

- `/proc/[PID]/fd/`에는 그 프로세스가 연 모든 파일이 **FD 번호를 이름으로 한 링크**로 존재한다
- 즉 원래 이름표는 사라졌어도 `/proc/470/fd/3` 같은 **커널과 직접 통하는 또 다른 이름표**가 남아 있다
- 이 링크를 통해 `truncate`하면, **프로세스를 건드리지 않고 내용물만 비워** 공간을 회수한다

```sh
sudo truncate -s 0 /proc/[PID]/fd/[fd번호]
# 예: sudo truncate -s 0 /proc/470/fd/3
```

### ④ 사용 중인 파일을 안전하게 비우는 정석 — logrotate

- **가장 권장**: 리눅스 거의 모든 배포판에 포함된 로그 관리 전문 유틸리티 **logrotate**
  - 설정 파일에 규칙(`copytruncate` 등)만 지정하면 삭제·압축·보관 주기를 가장 안전한 방식으로 처리
  - `copytruncate`: 로그를 복사해 백업한 뒤 **원본 파일은 truncate로 비우기**만 함 → 프로세스가 같은 FD를 계속 써도 안전
  - 직접 스크립트를 짜는 것보다 안정적이라 **표준 방식으로 강력 권장**
- logrotate를 못 쓰는 상황이면:

```sh
# 파일이 아직 존재하면 → 내용만 비우기 (프로세스 중단 없이 즉시 공간 확보)
truncate -s 0 [파일명]
```

  - 이미 `rm`으로 지워버렸다면 → 위 "/proc 비상 통로" 사용

## df와 du의 용량이 다를 때

`df`와 `du`는 측정 관점이 달라 결과가 다를 수 있다.

| 명령 | 측정 레벨 | 기준 |
|------|----------|------|
| **df** | 파일시스템 레벨 | 파일시스템이 "사용 중"이라 표시한 전체 블록 |
| **du** | 파일 레벨 | 실제로 **이름이 존재하는** 파일들의 크기 합산 |

좀비(삭제 대기) 파일이 있으면 둘이 크게 차이 난다.

- **df**: 프로세스가 붙잡은 `(deleted)` 파일의 공간도 "사용 중"으로 집계
- **du**: 이름이 사라진 파일은 집계 못 함
- 따라서 **`df 결과 > du 결과`** 현상 발생 → **좀비 파일 존재의 강력한 신호**

```sh
# 둘을 비교해 좀비 파일 존재를 간접 확인
df -h /
du -sh /
# 차이가 크면 좀비 파일이 디스크를 잡아먹고 있을 가능성이 높다
```

## Inode 고갈 — 용량은 남는데 파일이 안 만들어질 때

### Inode란

- 파일 하나당 inode 하나가 할당된다
- 파일시스템 생성 시 inode 총 개수가 정해지며, 이후 **늘릴 수 없다**(ext4 기준)
- 즉 **디스크 용량과 별개로 inode에도 한도**가 있다

> 비유: 주차장에 빈 공간(디스크 용량)은 많은데, 발급할 수 있는 **주차권(inode)** 이 다 떨어진 상황. 차를 더 댈 자리는 있어도 표를 못 줘서 못 들어온다.

### 증상

- 디스크 용량은 충분한데 파일 생성이 안 됨
- **"No space left on device"** 에러가 나는데 `df -h`로는 여유 공간이 있음
- 주로 **작은 파일이 수십~수백만 개** 쌓일 때 (세션 파일·캐시·메일 큐 등)

### 확인

```sh
df -i          # -i: inode 사용량 표시. IUse%가 100%면 고갈
```

```sh
# 어느 디렉토리에 파일이 많은지 — 개수 세서 많은 순 정렬
find [경로] -xdev -type f | cut -d "/" -f 2-3 | sort | uniq -c | sort -rn | head -20
```

### 해결

- 불필요한 파일을 대량 삭제해 inode 회수
- 근본적으로는 **작은 파일이 대량 생성되는 원인**을 제거 (캐시 정리 크론잡, 세션 만료 설정 등)

## Swap 공간

### Swap이란

- 물리 메모리(RAM)가 부족할 때 **디스크 일부를 임시 메모리처럼 사용**하는 공간
- RAM에서 당장 안 쓰는 데이터를 디스크로 내보내고(swap out), 필요할 때 다시 가져온다(swap in)
- 디스크는 RAM보다 훨씬 느려, **swap 사용량이 높으면 성능이 크게 저하**된다

> 비유: 책상(RAM)이 좁아 당장 안 보는 책을 바닥(디스크)에 내려놓는 것. 필요하면 다시 올리지만, 매번 허리 굽혀 줍느라 작업이 느려진다.

### 확인

```sh
free -h          # 메모리와 swap 사용량 한눈에 (total/used/free)
swapon --show    # swap 파티션/파일 상세 정보
```

### Swap 사용량이 높을 때

물리 메모리 부족 신호이므로, 메모리를 많이 쓰는 프로세스부터 확인한다.

```sh
# 메모리 사용량 순으로 프로세스 정렬
ps aux --sort=-%mem | head -20
```

- 근본 해결: **메모리 증설**(인스턴스 스펙 업) 또는 메모리 누수 프로세스 수정
- swap 자체를 늘리는 건 임시방편이지 근본 해결이 아니다
