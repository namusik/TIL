# Graphify (코드베이스 지식 그래프)

> 최종 업데이트: 2026-07-16 | Graphify (YC S26) 기준

## 개념

Graphify는 **코드베이스와 문서·SQL 스키마·설정·PDF를 하나의 쿼리 가능한 지식 그래프로 변환**해, AI 코딩 에이전트가 파일을 일일이 grep하는 대신 **관계망을 질의**하도록 해주는 도구다. `/graphify .` 한 줄로 프로젝트 전체 구조와 관계를 지도화한다.

> 낯선 도시에서 길을 찾는 것과 같다. 골목마다 직접 걸어다니며(grep·파일 읽기) 지리를 익히는 대신, **지하철 노선도(그래프)** 를 보면 "인증에서 DB까지 어디로 연결되나"를 한눈에 따라갈 수 있다.

## 배경

- **Graphify Labs**(Y Combinator S26 배치)가 만든 오픈소스 스킬.
- 문제의식은 명확하다 — LLM으로 큰 코드베이스를 다루면 누구나 같은 벽에 부딪힌다. **컨텍스트 창은 유한한데 코드베이스는 무한**해서, 에이전트가 방향을 잡으려 수십 개 파일을 다시 읽는다.

## 문제의식 — grep의 한계

Claude Code 같은 에이전트는 기본적으로 grep·파일 읽기로 컨텍스트를 모은다. 큰 코드베이스에서는 이 방식이 무너진다.

- **관련 파일을 놓친다** — 연결을 전부 훑지 못해 영향받는 곳을 빠뜨린다
- **잘못된 가정을 한다** — 부분만 보고 전체 구조를 오해한다
- **토큰을 낭비한다** — 방향 잡기용으로 파일을 반복해 읽는다

Graphify는 **관계를 그래프로 미리 만들어**, 영향받는 곳을 관계망으로 정확히 따라가게 해 이 실수들을 줄인다.

## 어떻게 동작하나

핵심은 **코드는 LLM 없이 로컬에서 결정적으로 파싱**한다는 점이다.

- **tree-sitter AST 파싱** — 36개 언어를 tree-sitter로 파싱해 그래프를 만든다. **결정적이고, LLM을 쓰지 않으며, 아무것도 기계 밖으로 나가지 않는다.**
- **문서·미디어만 LLM 사용** — PDF·이미지·영상 자막 등 의미 추출이 필요한 것만 설정된 LLM API(Ollama·OpenAI·Claude·Gemini·Bedrock)를 선택적으로 쓴다.

코드의 구조적 관계는 추측이 아니라 **파서가 확정한 사실**로 뽑는다는 게 신뢰의 근거다.

## 엣지 신뢰도 태그

그래프의 각 연결(엣지)에는 **어떻게 알아냈는지**가 태그로 붙는다. LLM 소비자에게 이 구분이 특히 유용하다.

| 태그 | 의미 |
|------|------|
| **EXTRACTED** | 코드에서 **명시적으로 발견**한 관계 (확정 사실) |
| **INFERRED** | 정황으로 **추론**한 관계 |
| **AMBIGUOUS** | 모호해서 단정할 수 없는 관계 |

→ 에이전트는 `EXTRACTED`는 **사실로 신뢰**하고, `INFERRED`는 **유보적으로** 다룰 수 있다. "찾은 것 vs 추측한 것"을 구분해주는 것이다.

## 커뮤니티 탐지

- **Leiden 알고리즘**으로 그래프를 **서브시스템(커뮤니티)**으로 자동 분할해, 큰 코드베이스를 논리적 덩어리로 파악하게 한다.
- **"god node"** 식별 — 가장 많이 연결되어 **모든 흐름이 지나는 핵심 노드**를 찾아준다. 여기가 바뀌면 영향 범위가 크다는 신호다.

## 출력물

세 가지 형태로 결과를 낸다.

| 출력 | 용도 |
|------|------|
| **HTML 그래프** | 인터랙티브 시각화 — 관계를 눈으로 탐색 |
| **Markdown 리포트** | 인사이트가 담긴 문서 |
| **JSON 그래프 데이터** | 에이전트·도구가 프로그램으로 질의 |

## 사용법

- **`/graphify .`** 스킬로 실행 — Claude Code, Cursor, Codex, Gemini CLI, GitHub Copilot 등 **15개 이상 에이전트** 지원
- **MCP 서버** 제공 — 에이전트가 그래프를 프로그램으로 질의 (→ [MCP 서버](MCP-서버.md))
- **Git hook** 연동 — 커밋 시 그래프 **자동 재빌드**로 최신 유지
- **벡터 스토어 불필요** — 그래프 자체가 구조. 별도 임베딩 인프라 없이 동작

## 왜 유용한가

- **영향도 분석** — 신규 기능·수정 시 관계망으로 영향받는 곳을 정확히 추적
- **문서 ↔ 코드 연결** — 설계 문서를 코드와 함께 관리하면, "이 모듈이 **어떤 결정으로** 작성됐는지" 히스토리·맥락까지 그래프로 따라감
- **토큰 절약** — 파일 재읽기 대신 필요한 노드·엣지만 질의 → 컨텍스트 소모 대폭 감소 (→ [컨텍스트 엔지니어링](../엔지니어링/컨텍스트-엔지니어링.md))
- **로컬·프라이버시** — 코드 파싱은 전부 로컬. 소스가 외부로 안 나감

## LLM Wiki와의 관계

비슷한 시기에 뜬 [LLM Wiki](../엔지니어링/LLM-Wiki.md)와 **경쟁이 아니라 상호보완**이다.

| | **Graphify** | **LLM Wiki** |
|---|-------------|-------------|
| 대상 | **코드베이스**(+docs·SQL·PDF) | **모든 지식 자료** |
| 산출물 | **지식 그래프**(노드·엣지) | **마크다운 위키**(페이지·링크) |
| 생성 방식 | AST **로컬 결정적 파싱** | LLM이 **읽고 이해해** 종합 |
| 강점 | 코드 구조·영향도의 **정확한 관계** | 판단·근거·이력의 **누적과 이해** |

공통 목표는 같다 — **grep·파일 재읽기로 컨텍스트를 긁어모으는 대신, 구조화된 지식을 질의**해 실수와 토큰을 줄이는 것. Graphify가 "코드의 관계망"을 준다면, LLM Wiki는 "왜 그렇게 결정했는가"의 맥락을 축적한다.

### 함께 쓰는 워크플로

**필수 조합은 아니다** — 코드 구조만 파악·정리할 거면 Graphify 하나로 충분하다. 다만 함께 쓰면 **"지금의 구조 + 왜의 맥락"**을 모두 남긴다.

1. **Graphify로 코드 그래프 생성** — 구조·영향도·god node 파악 (뭐가 어디 연결됐나)
2. **실제 작업** — 리팩터링·기능 추가·버그 수정
3. **LLM Wiki에 write-back** — "이 모듈은 X 결정으로 이렇게 됨", "이 버그 원인은 Y였음" 같은 판단·이력을 위키에 축적
4. **다음 세션** — LLM Wiki가 '왜'의 맥락을, Graphify가 '지금'의 최신 구조를 제공

Graphify는 **커밋마다 자동 재빌드**돼 항상 최신 구조를 주고, LLM Wiki는 **코드가 변해도 사라지지 않는 결정·이력**을 쌓는다. 어느 질문에 뭘 쓸지는 명확하다.

| 이런 질문엔 | 도구 |
|------------|------|
| "이 클래스 지우면 어디 깨지나" | **Graphify** (관계 추적) |
| "이 함수는 뭘 거쳐 DB까지 가나" | **Graphify** |
| "왜 이 구조로 설계했나, 트레이드오프는" | **LLM Wiki** (맥락) |
| "3주 전 이 증상 원인이 뭐였지" | **LLM Wiki** (이력) |

> Graphify는 **건물 도면**(지금 어떻게 생겼나), LLM Wiki는 **시공 일지**(왜 이렇게 지었나)다. 도면만 있어도 건물은 파악되지만, 일지가 있으면 "이 벽을 왜 여기 세웠는지"까지 안다.
