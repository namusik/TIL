# LLM Wiki (에이전트 지식 관리 패턴)

> 최종 업데이트: 2026-07-16 | Andrej Karpathy LLM Wiki 패턴 기준

## 개념

LLM Wiki는 **AI가 원본 자료를 읽고 이해해서, 구조화된 마크다운 위키로 정리·연결·유지하며 지식을 축적**하는 지식 관리 패턴이다. 질문할 때마다 원본을 다시 뒤지는 대신(RAG), **한 번 이해한 것을 문서로 남겨 계속 쌓아간다.**

> 신입이 매번 창고에서 원자재를 찾아 헤매는 것(RAG)과, 선임이 정리해둔 **위키를 보고 바로 답하고, 새로 안 것을 다시 위키에 적어두는 것**(LLM Wiki)의 차이다. 위키는 볼수록 두꺼워지고 똑똑해진다.

핵심은 **"위키가 계속 축적되는 산출물(persistent, compounding artifact)"** 이라는 점이다. 문서가 늘수록 지식이 누적·구조화되어, 나중에는 단순 검색보다 훨씬 풍부한 답을 낸다.

## 배경/역사

- **2026.4** — **Andrej Karpathy**(OpenAI 창립 멤버·전 테슬라 AI 총괄)가 [GitHub Gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)로 제안. 며칠 만에 수천 스타를 받으며 AI 커뮤니티에서 화제가 됨.
- 문제의식: **RAG는 매 질문마다 백지에서 원본을 재검색**한다. 이미 이해한 지식을 버리는 셈이다. "이해한 것을 문서로 컴파일해 두고 계속 갱신하자"는 발상.

## RAG와의 차이 (핵심)

| | RAG (기존) | **LLM Wiki** |
|---|-----------|-------------|
| 방식 | 질문마다 **원본을 재검색** | 미리 **위키로 정리해 축적** |
| 산출물 | 없음 (매번 즉석) | **축적되는 위키** |
| 교차 참조 | 매번 재발견 | **설계상 이미 존재** |
| 모순 | 드러나지 않음 | **미리 표면화(flag)** |
| 시간이 지날수록 | 그대로 | **지식이 두꺼워짐** |

RAG가 "매번 원점에서 재발견"이라면, LLM Wiki는 "한 번 컴파일하고 최신으로 유지"다.

## 3계층 구조

| 계층 | 역할 |
|------|------|
| **Raw Sources** | 수집한 원본(문서·PDF·노트·로그). AI가 **읽되 절대 수정하지 않는** 진실의 원천 |
| **Wiki** | AI가 생성·소유하는 **마크다운 페이지 모음**. 개념·인물·프로젝트·결정을 **상호 링크된 페이지**로 조직. 지식이 여기서 누적 |
| **Schema** | 위키를 **어떻게 구축·유지할지 정한 규칙 문서**(`CLAUDE.md` 류). 명명 규칙, ingest/query/lint 워크플로 정의 |

## 세 가지 오퍼레이션

**Ingest (수집)** — 새 원본을 넣으면 AI가 읽고, 핵심을 사용자와 논의한 뒤, 요약 페이지를 쓰고, 인덱스를 갱신하고, 관련 엔티티 페이지를 수정한다. **원본 하나로 10~15개 위키 페이지를 손댈 수 있다.**

**Query (질의)** — 이미 종합된 위키에 질문한다. AI가 관련 페이지를 찾아 **인용과 함께** 답하므로, RAG의 "매번 원점에서 재발견" 문제가 없다.

**Lint (정리)** — 주기적 건강 점검. **모순·낡은 주장·고아 페이지(orphan)·누락된 교차 참조**를 찾아내 위키가 커져도 정돈된 상태를 유지한다.

## 운영을 지탱하는 규칙

LLM에게 **유지보수 비용이 거의 0**이라는 점이 이 패턴을 가능케 한다. LLM은 교차 참조 갱신을 잊지 않고, 모순 표시를 빠뜨리지 않는다.

- **Write-back** — 질의로 얻은 가치 있는 종합 결과를 새 페이지로 위키에 되써넣는다. 탐색이 지식 베이스로 축적된다.
- **모순 표면화 (덮어쓰기 금지)** — 새 자료가 기존 주장과 충돌하면 조용히 덮어쓰지 않고, 그 긴장(tension)을 **명시적으로 표시**한다.
- **Schema 공진화** — 사람과 AI가 함께 스키마를 다듬으며, 자기 도메인에 맞는 규칙을 문서화해 나간다.

## 인프라

| 요소 | 역할 |
|------|------|
| **Index.md** | 페이지 링크 + 한 줄 요약의 목록. 매 ingest 시 갱신 |
| **Log.md** | ingest·query·유지보수의 **append-only 시간순 기록** |
| **Git** | 위키 버전 관리 — 이력·협업 |
| **Obsidian** | (선택) 페이지·링크를 **그래프로 시각화**해 탐색. 마크다운이라 직접 수정도 쉬움 |

## 참고 — Graphify와의 관계

비슷한 시기에 뜬 **Graphify**(Y Combinator S26)와 자주 함께 언급된다. 둘은 **경쟁이 아니라 상호보완**이다.

| | **Graphify** | **LLM Wiki** |
|---|-------------|-------------|
| 대상 | **코드베이스**(+docs·SQL·PDF) | **모든 지식 자료** |
| 산출물 | **지식 그래프**(노드·엣지) | **마크다운 위키**(페이지·링크) |
| 생성 방식 | tree-sitter **AST로 로컬 결정적 파싱**(코드는 LLM 미사용), 엣지에 `EXTRACTED`/`INFERRED` 태그 | LLM이 **읽고 이해해** 페이지로 종합 |
| 강점 | 코드 구조·영향도의 **정확한 관계 추적** | 판단·근거·이력의 **누적과 이해** |

공통 목표는 같다 — **grep·파일 재읽기로 컨텍스트를 긁어모으는 대신, 구조화된 지식을 질의**해 실수와 토큰을 줄이는 것. Graphify가 "코드의 관계망"을 주면, LLM Wiki는 "왜 그렇게 결정했는가"의 맥락을 축적한다.

> 코드 정리 시 **둘을 함께 쓰는 워크플로**(Graphify로 구조 파악 → 작업 → LLM Wiki에 맥락·이력 write-back)는 → [Graphify](../도구-통합/Graphify.md)의 "함께 쓰는 워크플로" 참고.
