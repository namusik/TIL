# 아키텍처 스펙트럼 — 모놀리스부터 MSA까지

> 최종 업데이트: 2026-07-16 | 모노레포 · 모듈러 모놀리스 · MSA 트렌드 기준

## 개념

"우리 시스템을 어떻게 쪼갤까"를 이야기할 때 **두 개의 다른 축**이 자주 뒤섞인다. 이 둘을 분리해야 논의가 명확해진다.

- **축① 배포 아키텍처** — 실행·배포 단위를 어떻게 나누나 → **모놀리스 → 모듈러 모놀리스 → MSA**
- **축② 코드 저장소** — 코드를 어디에 두나 → **모노레포 vs 폴리레포**

> "모노레포"와 "모놀리스"는 이름이 닮았지만 **다른 층위**다. 하나는 *코드를 어디 두느냐*(저장소), 하나는 *어떻게 배포하느냐*(실행 단위)다. 섞어 쓰면 대화가 엉킨다.

## 두 축은 직교한다 (핵심)

두 축은 서로 독립이다. 어떤 조합도 가능하다.

| | **모노레포** (한 저장소) | **폴리레포** (저장소 분리) |
|---|---|---|
| **모놀리스** | 단순 앱 | (드묾) |
| **모듈러 모놀리스** | ⭐ 요즘 흔한 시작점 | 가능 |
| **MSA** | **Google식** — 한 레포에 수천 서비스 | **Netflix식** — 서비스마다 레포 |

즉 **MSA라고 반드시 레포를 쪼개는 게 아니다.** 구글은 거대한 **모노레포 안에서 수천 개의 마이크로서비스**를 운영한다. 반대로 폴리레포로 모놀리스를 둘 수도 있다.

## 축① 배포 아키텍처 스펙트럼

| | 배포 단위 | 경계 강제 | 모듈 간 통신 | 운영 복잡도 |
|---|---|---|---|---|
| **모놀리스** | **1개** | 없음(관행에 의존) | 메서드 호출 | 낮음 |
| **모듈러 모놀리스** | **1개** | **모듈**(정적 분석·이벤트) | 메서드·도메인 이벤트 | 중간 |
| **MSA** | **N개** | **네트워크·API** | HTTP·gRPC·메시지 | 높음 |

### 모놀리스

하나의 배포 단위에 모든 기능이 들어간다. 단순하고 빠르게 시작할 수 있지만, 커질수록 **경계가 무너져** 한 곳의 변경이 사방에 번진다(현재 `megabird-direct-send-engine`의 벤더 뒤섞임이 이 증상).

### 모듈러 모놀리스

여전히 **하나의 배포 단위**지만, 내부를 **모듈로 나누고 그 경계를 강제**한다. "모듈 A는 B의 내부를 직접 못 건드린다"를 빌드·정적분석으로 막는다. **MSA의 복잡성 없이 경계의 이점**을 얻는 중간 지대다.

- 경계 강제 도구: **Spring Modulith**, **ArchUnit**, **jMolecules**
- 구현 형태: [Gradle 멀티모듈](../Spring/Gradle/gradle-멀티모듈.md)로 모듈을 물리적으로 분리

### 마이크로서비스 (MSA)

기능을 **독립 배포·독립 스케일되는 여러 서비스**로 쪼갠다. 경계가 네트워크로 강제되어 가장 강력하지만, 분산 트랜잭션·관측성·운영 부담이 크다. (상세 → [MSA란](MSA란.md))

## 축② 코드 저장소 — 모노레포 vs 폴리레포

| | 모노레포 (한 저장소) | 폴리레포 (저장소 분리) |
|---|---|---|
| 코드 공유 | 쉬움 (한곳) | 어려움 (패키지 배포) |
| 교차 변경 | **원자적 커밋** 한 번 | 여러 레포 조율 |
| 팀 자율성 | 낮음 | **높음** |
| Blast radius(영향 범위) | 큼 | **작음** |
| 릴리스 조율 | 통합 | 서비스마다 버전·호환성 관리 |
| 필수 조건 | **전용 빌드 도구** 없으면 지옥 | 상대적으로 단순 |

대규모 기업 실태는 갈린다.

| 방식 | 채택 기업 |
|------|-----------|
| **모노레포** | Google(80TB, Bazel), Meta(Buck2), Microsoft, Airbnb, Uber, X |
| **폴리레포** | Netflix, Spotify (서비스·팀 자율성) |

### 모노레포를 지탱하는 기술

거대 레포를 견딜 만하게 만드는 핵심은 **"바뀐 것만 빌드·테스트"**다.

- **의존성 그래프** — 무엇이 무엇에 의존하는지 정밀 추적
- **Affected builds** — 변경에 영향받는 대상만 재빌드
- **Remote caching** — 한 번 빌드한 결과를 팀·CI가 공유
- **Remote execution** — 빌드를 여러 머신에 분산(Bazel)

| 도구 | 유형 | 대상 규모 | 의존 모델 |
|------|------|-----------|-----------|
| **Bazel / Buck2 / Pants** | polyglot heavyweight | 대규모·다언어 (1,000+ 엔지니어) | **소스·타겟 레벨**(정밀), hermetic 빌드 |
| **Nx** | 고급 task runner | 중대형 (~500 패키지) | 패키지 레벨 + 프로젝트 그래프·아키텍처 규칙 |
| **Turborepo** | 경량 task runner | 소중형 JS/TS (5~50 패키지) | 패키지 레벨, 빠른 셋업, Vercel 통합 |

## 2026 트렌드

### 모듈러 모놀리스 회귀 — "마이크로서비스 후회"

2026년 가장 큰 아키텍처 변곡점이다.

> **CNCF 2026 Q1 보고서 — MSA를 도입했던 조직의 42%가 일부 서비스를 다시 큰 배포 단위로 합쳤고, 그 형태가 모듈러 모놀리스였다.**

- Neal Ford·Sam Newman(MSA 담론 대가들)이 2026을 **"모놀리스의 르네상스"**로 선언
- **Shopify**가 모듈러 모놀리스로 Black Friday **30TB/분** 처리
- **Spring Modulith 1.4 GA**(2026-03) 등 진화적 아키텍처 도구 성숙

핵심 교훈: **"경계 긋기"가 분산 시스템의 가장 어려운 문제**인데, 성급히 MSA로 쪼개면 잘못 그은 경계를 되돌리기 어렵다. 모듈러 모놀리스는 **경계를 싸게 실험**하다가, 진짜 필요할 때 모듈을 서비스로 떼어내는 진화적 중간 지대다.

### 모노레포 르네상스 — AI가 당긴 방아쇠

모노레포가 다시 강해지는 데 **AI 코딩 어시스턴트**가 결정적 이유로 추가됐다. **통합된 코드베이스 컨텍스트**에서 AI가 훨씬 정확히 추론·리팩터링하기 때문이다.

이는 앞서 뜬 [Graphify](../AI/도구-통합/Graphify.md)(코드 지식 그래프)·[LLM Wiki](../AI/엔지니어링/LLM-Wiki.md)(지식 위키)가 화제가 된 맥락과 정확히 같다 — 그래프·위키는 **지식이 한곳에 모일수록** 위력이 커진다.

## 선택 가이드 — 어디서 시작하나

| 단계 | 형태 | 경계 강제 | 2026 권장 |
|:---:|------|-----------|:---:|
| 1 | 단일 모놀리스 | 없음 | 소규모만 |
| 2 | **멀티모듈 / 모듈러 모놀리스** (한 레포·한 배포) | 빌드 의존·정적분석 | ⭐ **여기서 시작** |
| 3 | 모노레포 + 모듈별 배포 | 빌드 그래프 | 대규모 시 |
| 4 | 폴리레포 / MSA (레포·서비스 분리) | 네트워크·API | **필요가 증명될 때만** |

원칙은 하나다 — **왼쪽에서 시작해, 오른쪽으로는 필요가 증명될 때만 이동한다.** "성급한 분리"는 2026 들어 오히려 피하는 방향이다. 한 레포·한 배포 안에서 **모듈로 경계부터 잡는 것**이 지금의 정석이다.
