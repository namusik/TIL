# MySQL 날짜·시간 저장 — 타입과 타임존

> 최종 업데이트: 2026-06-23 | MySQL 8.0 · Connector/J 8.x 기준

## 개념

MySQL에서 시간을 저장할 때 핵심은 두 가지다 — **어떤 타입을 쓰는가**(`DATETIME` vs `TIMESTAMP`)와 **타임존을 어떻게 다루는가**. 이 둘이 "DB에 박힌 값이 결국 어느 순간을 가리키는지"를 결정한다.

> 비유: 시각을 적는 두 방식이다. 하나는 **"벽시계에 보이는 숫자 그대로"**(`DATETIME`) 적는 것이고, 다른 하나는 **"전 세계 공통 기준(UTC)으로 환산해서"**(`TIMESTAMP`) 적는 것이다. 전자는 어느 동네 시계인지 모르고, 후자는 어디서 읽어도 같은 순간이다.

## 날짜·시간 타입

| 타입 | 저장 내용 | 범위 | 타임존 |
|------|----------|------|--------|
| `DATE` | 날짜만 | 1000 ~ 9999 | 무관 |
| `TIME` | 시각/경과시간 | -838:59:59 ~ 838:59:59 | 무관 |
| `DATETIME` | 날짜+시각 | 1000 ~ 9999 | **무시(그대로 저장)** |
| `TIMESTAMP` | 날짜+시각 | **1970 ~ 2038** | **인식(UTC 변환)** |
| `YEAR` | 연도 | 1901 ~ 2155 | 무관 |

`DATETIME`·`TIMESTAMP`는 MySQL 5.6.4+부터 소수 초를 최대 6자리(마이크로초)까지 저장한다(`DATETIME(3)` 등).

## DATETIME vs TIMESTAMP — 핵심

같은 "날짜+시각"을 담지만 **타임존 처리가 정반대**라, 이 선택이 시간 저장의 성패를 가른다.

| | `DATETIME` | `TIMESTAMP` |
|---|---|---|
| 타임존 변환 | **없음** — 입력값 그대로 박제 | UTC로 변환 저장 → 조회 시 세션 타임존으로 역변환 |
| 성격 | 벽시계 값(타임존 미상) | 절대 시점(instant) |
| 범위 | 1000 ~ 9999 | **1970 ~ 2038 (Y2K38 한계)** |
| 저장 크기 | 5바이트(+소수초) | 4바이트(+소수초) |
| 세션 타임존 영향 | 안 받음 | **받음** |

- **`TIMESTAMP`** 는 "이건 지구상 한 순간이다"를 DB가 책임진다. 저장 시 세션 타임존 기준으로 해석해 **UTC로 정규화**하고, 조회 시 다시 세션 타임존으로 돌려준다. 그래서 **세션 타임존이 바뀌면 같은 행도 다른 시각으로 보인다**. 단 32비트라 **2038년 문제**가 있다.
- **`DATETIME`** 은 DB가 타임존을 신경 쓰지 않고 **받은 값 그대로** 넣고 뺀다. `2024-05-15 00:00:00`을 넣으면 어느 세션에서 읽어도 글자 그대로다. 대신 "이게 한국 시각인지 UTC인지"는 **애플리케이션이 책임**져야 한다.

핵심은 — `TIMESTAMP`는 DB가 타임존을 알아서 변환해주는 대신 세션 타임존에 흔들리고, `DATETIME`은 흔들리지 않는 대신 타임존 의미를 앱이 떠안는다는 것이다.

### 오프셋이 붙은 입력은 변환된다 (MySQL 8.0.19+)

위의 "그대로 저장"은 **오프셋 없는 순수 입력**일 때다. MySQL 8.0.19부터 datetime 리터럴에 오프셋을 붙일 수 있는데(`'2024-05-15 00:00:00+09:00'`), 오프셋이 명시되면 그 기준으로 **해석해 변환**한다.

| 입력 (세션 타임존 = UTC 가정) | `DATETIME` 저장 결과 |
|------|------|
| `'2024-05-15 00:00:00'` (오프셋 없음) | `2024-05-15 00:00:00` — 그대로 |
| `'2024-05-15 00:00:00+09:00'` (오프셋 있음) | `2024-05-14 15:00:00` — `+09`를 UTC로 환산 |

- 오프셋이 **없으면** 해석 기준이 없어 그대로 저장하고, **있으면** 그 오프셋 기준 시각을 **세션 타임존으로 환산**해 저장한다.
- 단 `DATETIME`엔 오프셋을 담을 칸이 없어 **환산된 값만 남고 `+09:00` 꼬리표는 버려진다**(`TIMESTAMP`는 UTC로 변환 저장). 그래서 ISO 8601처럼 오프셋이 값에 보존되지는 않는다.
- 8.0.18 이하에선 오프셋을 붙이면 에러·잘림이다.

## 타임존 변수 세 가지

`TIMESTAMP`의 변환은 **세션 타임존**을 기준으로 일어난다. 관련 변수는 셋이다.

```sql
SELECT @@global.time_zone, @@session.time_zone, @@system_time_zone;
```

| 변수 | 의미 |
|------|------|
| `@@global.time_zone` | 서버 전체 기본 타임존(모든 새 세션의 기본값). RDS/Aurora는 파라미터 그룹의 `time_zone` 값 |
| `@@session.time_zone` | **현재 커넥션만의 타임존.** 접속 시 global을 복사하며, `SET time_zone='+00:00'` 으로 개별 변경 가능 |
| `@@system_time_zone` | OS의 실제 시간대. RDS는 보통 **UTC로 고정** |

물리적 OS 시간(`@@system_time_zone`)은 UTC로 두고, 그 위에서 MySQL이 논리적으로 KST 등으로 해석하는 구성이 일반적이다.

세 변수의 관계와 "어느 게 변환 기준이냐"는 이렇다.

```mermaid
flowchart LR
    G["@@global<br/>서버 기본값"] -->|접속 시 복사| S["@@session<br/>변환 기준 ★"]
    S -->|값이 'SYSTEM'이면| SY["@@system<br/>OS 시간대"]
```

- 모든 변환(`TIMESTAMP`의 UTC 정규화, `DATETIME`의 오프셋 환산)은 **`@@session.time_zone`** 을 기준으로 일어난다.
- `@@global`은 새 세션의 초기값을 복사해줄 뿐, 변환에 직접 쓰이지 않는다. `SET time_zone='+00:00'`으로 세션 값을 바꾸면 그 커넥션의 변환 기준이 즉시 바뀐다.
- **함정** — `@@session.time_zone`을 조회했을 때 `'SYSTEM'`으로 나오면(MySQL 기본값), 세션은 OS 시간대(`@@system_time_zone`)를 그대로 따라간다. 이 경우 실제 변환 기준은 `'SYSTEM'` → OS 값이 된다.
  - 헷갈리기 쉬운 점 — 세션이 `'SYSTEM'` 값을 갖게 된 **출처**는 global 복사가 맞지만, `'SYSTEM'`이 **가리키는 시계**는 global이 아니라 `@@system_time_zone`(OS)다. `'SYSTEM'`은 "global을 보라"가 아니라 **"OS를 따르라"는 키워드**이기 때문이다. 게다가 복사는 접속 순간 1회뿐이라, 접속 후 누가 `SET GLOBAL`로 global을 바꿔도 기존 세션은 따라가지 않는다.

## TIMESTAMP의 UTC 변환 흐름

아래는 `TIMESTAMP` 컬럼에만 해당한다(`DATETIME`은 변환 없이 그대로 들고난다).

```mermaid
flowchart LR
    A["앱: LocalDateTime<br/>(타임존 정보 없음)"] -->|드라이버가 문자열 전송| B["MySQL: 세션 타임존으로<br/>로컬시각 해석"]
    B -->|정규화| C["내부 저장: UTC"]
    C -->|세션 타임존으로 변환| D["반환: 로컬시각 문자열"]
    D -->|드라이버 매핑| E["앱: LocalDateTime"]
```

**저장(INSERT)**

1. JDBC 드라이버는 타임존 정보 없는 `LocalDateTime`을 `'YYYY-MM-DD HH:MM:SS'` 문자열로 그대로 MySQL에 전송한다.
2. MySQL이 그 문자열을 `@@session.time_zone` 기준 로컬시각으로 **해석(interpretation)** 한다.
3. 그 값을 **UTC로 변환(normalization)** 해 내부에 저장한다.

→ 실제 UTC 변환을 수행하는 건 **DB**이고, 드라이버는 "서버가 어떤 타임존일 것"이라고 가정만 한다.

**조회(SELECT)**

1. MySQL이 내부 UTC 값을 읽는다.
2. `@@session.time_zone` 기준으로 로컬시각으로 변환한다.
3. 변환된 로컬시각이 JDBC로 반환되고, 드라이버가 다시 타임존 정보 없는 `LocalDateTime`으로 매핑한다.

## JDBC 연동 (Connector/J)

```
jdbc:mysql://aaa.ap-northeast-2.rds.amazonaws.com:3306/db?connectionTimeZone=Asia/Seoul
```

- 과거의 `serverTimezone`은 Connector/J 8.0.23+에서 **`connectionTimeZone`** 으로 대체됐다(`serverTimezone`은 별칭으로 여전히 동작).
- 이 값은 드라이버에게 **"서버 세션 타임존을 이렇게 간주/설정하라"** 는 힌트다. 실제 DB로 넘길 땐 자바에서 받은 로컬시각을 그대로 전달하고, 변환 기준 해석에만 이 값을 참고한다.
- `LocalDateTime`은 타임존이 없는 순수 시·분·초라, 드라이버는 이 설정을 참고해 해석한다. 시점(instant) 보존 동작은 `preserveInstants` 옵션으로 제어한다.

## 실무에서 무엇을 쓰나

가장 안전한 원칙은 **UTC로 저장하고, 사용자에게 보여줄 때만 지역 시각으로 변환**하는 것이다. 그래야 글로벌로 확장돼도 저장된 데이터가 흔들리지 않는다. 구현은 보통 둘 중 하나다.

| 전략 | 방법 | 특징 |
|------|------|------|
| **TIMESTAMP + 세션 UTC** | 세션 타임존을 UTC로 두면 DB가 자동으로 UTC 정규화 | 자동 변환 편리하나 **2038 한계** |
| **DATETIME + 앱에서 UTC 통일** | 앱이 항상 UTC 시각을 넣고 읽음 | 세션 타임존에 안 흔들리고 2038 없음. 많은 팀이 선호 |

- `connectionTimeZone`(구 `serverTimezone`) 옵션은 **DB 세션 타임존과 앱 타임존이 어긋날 때** 해석을 맞추는 안전장치다. 둘이 이미 UTC로 일치한다면 사실상 넣을 필요가 없다.
- KST를 그대로 저장해두면, 글로벌 전환 시점에 **전 데이터를 보정**해야 하는 부담이 생긴다. 처음부터 UTC로 저장하고 표시 단계에서 `Asia/Seoul` 등으로 변환하는 구조가 정석이다.
