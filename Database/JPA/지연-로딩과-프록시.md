# 지연 로딩과 프록시 (Lazy Loading & Proxy)

> 최종 업데이트: 2026-07-06 | Hibernate ORM 7.x 기준

## 개념

지연 로딩(Lazy Loading)은 연관 엔티티를 **실제 사용하는 시점까지 조회를 미루는** 전략이다. 미루는 동안 그 자리엔 진짜 객체 대신 **프록시(가짜 대역)** 를 넣어둔다.

> 식당 메뉴판과 같다. 메뉴판엔 사진과 이름만 있고(프록시), 실제 **주문해야(접근)** 요리가 주방에서 나온다(초기화). 안 시킨 메뉴는 조리하지 않으니 낭비가 없다.

반대는 즉시 로딩(EAGER)으로, 엔티티를 조회할 때 연관도 즉시 함께 가져온다.

| 전략 | 동작 | 연관은 언제 조회되나 |
|------|------|----------------------|
| **지연 (LAZY)** | 프록시만 넣어둠 | 실제 접근하는 순간 |
| **즉시 (EAGER)** | 함께 조회 | 엔티티 조회 시 바로 |

```java
Post post = postRepository.findById(1L).get();  // 게시글만 조회, author는 프록시
String name = post.getAuthor().getName();        // ← 이 순간 author 쿼리 발생
```

## 프록시란

프록시는 Hibernate가 **원본 엔티티를 상속해 만든 가짜 자식 객체**다(런타임에 바이트코드로 생성, ByteBuddy 사용). 내부엔 식별자(id)만 들고 나머지 필드는 비어 있다가, 실제 필드에 접근하는 순간 DB를 조회해 채운다(**초기화**). 한 번 초기화되면 이후 접근은 그 값을 재사용한다.

```java
Post post = repo.findById(1L).get();   // author 자리에 프록시(id=10, 나머지 빈 값)
post.getAuthor().getName();            // 첫 접근 → SELECT ... WHERE id=10 → 프록시 채움(초기화)
post.getAuthor().getEmail();           // 재접근 → 이미 초기화됨, 쿼리 없음
```

## 프록시의 성질

**① 연관마다 별개의 프록시다.** 게시글 N건을 조회하면 각 게시글이 자기 author 프록시를 하나씩 물어 프록시도 N개가 된다. 서로 다른 작성자를 가리키는 별개 객체라, 하나를 초기화해도 나머지는 채워지지 않는다.

| 게시글 | author 프록시 | 가리키는 작성자 |
|--------|--------------|-----------------|
| posts[0] | 프록시 A | author_id = 10 |
| posts[1] | 프록시 B | author_id = 20 |
| posts[2] | 프록시 C | author_id = 30 |

A를 초기화해도 B·C는 그대로라 각각 따로 조회된다 → N번. 이것이 [N+1 문제](N+1-문제.md)의 근본 원인이다. (단, 셋이 같은 작성자를 가리키면 첫 조회 후 1차 캐시에 올라가 나머지는 쿼리가 생략된다.)

**② `getId()`는 초기화를 일으키지 않는다.** 프록시가 식별자는 이미 갖고 있어서, 연관의 PK만 필요하면 쿼리 없이 꺼낼 수 있다.

**③ 타입 비교에 주의한다.** 프록시는 원본의 자식 타입이라 `entity.getClass() == Author.class`가 `false`다. `instanceof`로 비교하거나 `Hibernate.unproxy()`로 원본을 꺼내 다룬다.

**④ 초기화 여부는 확인할 수 있다.** `Hibernate.isInitialized(proxy)`로 프록시가 이미 초기화됐는지 검사한다.

## 기본 로딩 전략

JPA 표준 기본값이 연관 종류마다 다르므로, 실무에서는 헷갈리지 않게 전부 LAZY로 명시한다.

| 연관 | JPA 기본 |
|------|----------|
| `@ManyToOne`, `@OneToOne` | EAGER (즉시) |
| `@OneToMany`, `@ManyToMany` | LAZY (지연) |

```java
@ManyToOne(fetch = FetchType.LAZY)  // 기본이 EAGER라 반드시 명시
private Author author;
```

즉시 로딩(EAGER)을 지양하는 이유는 명확하다. 필요 없을 때도 **항상 연관을 끌고 와** 비효율적이고, 연관이 연관을 물면 조회 한 번에 테이블이 줄줄이 딸려온다. 게다가 EAGER로 바꿔도 **N+1은 그대로** 발생한다. 그래서 **전부 LAZY로 막아두고 필요한 조회에서만 fetch join**하는 것이 정석이다.

## LazyInitializationException

지연 로딩의 대표 함정이다. 프록시는 **영속성 컨텍스트(트랜잭션 세션)가 살아 있을 때만** 초기화된다. 트랜잭션이 끝난 뒤(컨트롤러·뷰 렌더링 단계 등) 프록시를 처음 건드리면 이 예외가 터진다.

```
org.hibernate.LazyInitializationException: could not initialize proxy - no Session
```

대응 방법은 세 가지다.

- **fetch join / @EntityGraph** — 트랜잭션 안에서 필요한 연관을 미리 초기화 (가장 권장)
- **DTO 변환** — 트랜잭션 안에서 필요한 값만 DTO로 옮겨 밖으로 내보냄
- **OSIV (Open Session In View)** — 뷰 렌더링까지 세션을 열어둠. 단 커넥션을 오래 물어 실무에서는 끄는 추세
