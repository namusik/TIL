# N+1 문제 (N+1 Query Problem)

> 최종 업데이트: 2026-07-05 | Spring Data JPA / Hibernate 6.x 기준

## 개념

N+1 문제는 연관 데이터를 가져올 때, **쿼리 1번이면 될 것을 `1 + N`번 날리는** 성능 문제다.

- **1** = 목록을 조회하는 쿼리 (예: 게시글 10건)
- **N** = 그 목록의 **각 건마다** 연관 데이터를 가져오려고 추가로 나가는 쿼리 (예: 각 게시글의 작성자 10번)

게시글 10건이면 총 **11번**, 1000건이면 **1001번**. 데이터가 늘수록 쿼리가 선형으로 폭증한다.

> 장 보러 가서 물건 10개를 사는데, 카트에 한 번에 담아 계산대에서 한 번 결제(JOIN 1번)하면 될 걸, 물건 하나 집을 때마다 계산대로 뛰어가 따로 결제(N번)하는 꼴이다.

ORM만의 문제로 오해하기 쉽지만, MyBatis·순수 SQL에서도 **"목록 뽑고 반복문 돌며 건건이 상세 조회"** 패턴이면 똑같이 발생한다. 다만 JPA의 지연 로딩이 이걸 **눈에 안 보이게** 유발해서 특히 자주 밟는다.

## 왜 발생하나 — 지연 로딩

JPA에서 `@ManyToOne`, `@OneToMany` 같은 연관관계는 (실무 권장 설정상) **지연 로딩(Lazy Loading)** 이 기본이다. 연관 엔티티 자리에는 실제 데이터 대신 **프록시**가 들어 있다가, 그 필드에 **실제로 접근하는 순간** 쿼리가 나간다.

핵심은 `for` 문법 자체가 아니다. **목록 N건을 각각 하나씩 건드리는 것**이 원인이다.

```java
List<Post> posts = postRepository.findAll();  // ① 게시글 목록
for (Post post : posts) {
    System.out.println(post.getAuthor().getName());  // ② 각 건의 프록시를 하나씩 접근
}
```

나가는 쿼리를 **시간 순서대로** 보면 (게시글 3건 기준):

```sql
-- ① 목록 조회. 이 시점 author는 전부 프록시라 쿼리 없음
SELECT * FROM post;                     -- author_id = 10, 20, 30 반환

-- ② 반복하며 각 author 프록시를 처음 건드릴 때마다 개별 쿼리
SELECT * FROM author WHERE id = 10;     -- 1회차 접근
SELECT * FROM author WHERE id = 20;     -- 2회차 접근
SELECT * FROM author WHERE id = 30;     -- 3회차 접근
-- 합계 = 1 + 3
```

이렇게 N번이 되는 이유는 두 가지다.

- **각 건의 연관은 별개의 프록시**다. `posts[0].author`와 `posts[1].author`는 서로 다른 객체라, 각자 처음 접근할 때 **자기 것만** 조회한다 → 접근 횟수 = 쿼리 횟수.
- **JPA는 "앞으로 전부 쓸 것"임을 모른다.** 지금 필요한 하나만 가져오므로 `IN` 절로 묶지 못한다. (`batch size`가 바로 이 "미리 묶기"를 대신한다)

> 각 게시글이 자기만의 프록시를 하나씩 물고 있어 서로 다른 대상을 가리킨다는 점이 첫 번째 이유의 핵심이다. → [프록시의 정체와 성질](지연-로딩과-프록시.md)

뒤집으면 명확하다 — **연관을 아예 건드리지 않으면 N+1은 없다.** 지연 로딩이라 접근하는 순간에만 쿼리가 나가기 때문이다. 즉 방아쇠는 "목록 조회"가 아니라 **"조회한 목록의 연관을 하나씩 다 건드리는 행위"**다.

### for 문이 없어도 터진다

실무에서 가장 잘 속는 지점이다. 눈에 보이는 반복문을 안 써도, **프레임워크가 대신 각 요소의 연관에 접근**하면 똑같이 발생한다.

```java
@GetMapping("/posts")
public List<Post> list() {
    return postRepository.findAll();   // for 문이 없다
}
```

컨트롤러가 `List<Post>`를 JSON으로 직렬화할 때 Jackson이 각 `post.getAuthor()`를 호출 → N번 쿼리. Thymeleaf `th:each`, 스트림 `.map(p -> p.getAuthor())`도 마찬가지다. **"컬렉션의 각 요소마다 연관에 손대는 모든 것"이 곧 반복문**이며, `for` 문법의 유무는 상관없다.

## 두 가지 양상 — @ManyToOne vs @OneToMany

같은 N+1이라도 연관의 방향에 따라 **해결책이 달라진다.** 이걸 구분 못 하면 엉뚱한 처방을 한다.

| 양상 | 예 | 권장 해결 |
|------|-----|-----------|
| **단일 연관** (`@ManyToOne`, `@OneToOne`) | 게시글 → 작성자 1명 | **Fetch Join / @EntityGraph** (JOIN 한 방) |
| **컬렉션 연관** (`@OneToMany`, `@ManyToMany`) | 게시글 → 댓글 여러 개 | **Batch Size** (`IN` 절로 묶기) |

컬렉션에 fetch join을 쓰면 뒤에 설명할 **페이징·중복 문제**가 생기므로, 컬렉션은 batch size가 정석이다.

## 해결 방법

### Fetch Join — 연관을 애초에 JOIN해서 한 번에

JPQL `join fetch`로 연관 엔티티를 처음부터 함께 조회한다. 단일 연관(`@ManyToOne`)에 가장 효과적이다.

```java
@Query("SELECT p FROM Post p JOIN FETCH p.author")
List<Post> findAllWithAuthor();
```
```sql
-- 쿼리 1번으로 끝
SELECT p.*, a.* FROM post p JOIN author a ON p.author_id = a.id;
```

### @EntityGraph — Fetch Join을 선언적으로

같은 효과를 애너테이션으로 처리한다. Spring Data JPA 메서드에 붙이면 된다.

```java
@EntityGraph(attributePaths = "author")
List<Post> findAll();
```

### Batch Size — 컬렉션은 IN 절로 묶기

컬렉션 연관에서 개별로 나가던 N번의 쿼리를 `IN (...)` 한 방으로 묶는다. `1 + N`이 `1 + 1`이 된다. 전역 설정이 가장 편하다.

```yaml
# application.yml — 이 한 줄이 실무에서 제일 가성비 좋다
spring.jpa.properties.hibernate.default_batch_fetch_size: 100
```
```sql
-- 개별 조회 대신
SELECT * FROM comment WHERE post_id IN (1, 2, 3, ..., 100);
```

특정 연관에만 적용하려면 필드에 `@BatchSize`를 붙인다.

```java
@BatchSize(size = 100)
@OneToMany(mappedBy = "post")
private List<Comment> comments;
```

### DTO 프로젝션 — 필요한 것만 바로 조회

엔티티가 필요 없는 **조회 전용** 화면이라면, 처음부터 필요한 컬럼만 JOIN해서 DTO로 받는 게 가장 가볍다.

```java
@Query("SELECT new com.app.PostView(p.title, a.name) " +
       "FROM Post p JOIN p.author a")
List<PostView> findAllViews();
```

## 즉시 로딩(EAGER)은 답이 아니다

"Lazy라서 N+1이 나니 EAGER로 바꾸면 되지 않냐" — **아니다.** 즉시 로딩으로 바꿔도 **N+1은 그대로** 발생한다. Hibernate가 연관을 즉시 채우려고 결국 건건이 추가 쿼리를 날리기 때문이다. 오히려 EAGER는 **필요 없을 때도 항상 연관을 끌고 와** 성능을 더 망치므로, 실무에서는 **모든 연관을 LAZY로 두고 필요한 조회에서만 fetch join/batch size로 해결**하는 것이 정석이다.

## fetch join의 함정 — 컬렉션에 주의

fetch join이 만능은 아니다. **컬렉션(`@OneToMany`)** 을 fetch join할 때 두 가지 지뢰가 있다.

**① 페이징이 깨진다.** 컬렉션을 fetch join하면서 페이징(`Pageable`)을 걸면, Hibernate가 `firstResult/maxResults specified with collection fetch; applying in memory` 경고를 내뱉고 **전체 데이터를 메모리에 다 올린 뒤** 잘라낸다. 데이터가 크면 그대로 OOM이다. → 페이징이 필요한 컬렉션은 fetch join 대신 **batch size**를 쓴다.

**② 컬렉션 둘 이상은 못 한다.** `List` 컬렉션 두 개를 동시에 fetch join하면 `MultipleBagFetchException`이 터진다(카테시안 곱 방지). → `Set`으로 바꾸거나, 역시 **batch size**로 우회한다.

정리하면 — **단일 연관은 fetch join, 컬렉션은 batch size**가 안전한 기본 전략이다.

## 어떻게 감지하나

N+1은 조용히 숨어 있다가 데이터가 쌓인 운영 환경에서 터진다. **개발 단계에서 쿼리 수를 눈으로 확인하는 습관**이 최선의 방어다.

```yaml
# 나가는 SQL을 로그로 확인 (개발 환경)
logging.level.org.hibernate.SQL: debug
spring.jpa.properties.hibernate.format_sql: true
```

- **p6spy** 같은 라이브러리로 실제 실행 쿼리와 횟수를 한눈에 확인
- 테스트에서 **쿼리 카운트를 단언**(assert)해 회귀 방지 — 예: Hibernate `Statistics`의 `getPrepareStatementCount()`로 "이 API는 쿼리 2번 이내" 검증
