# 데이터베이스 인덱스 (Index)

> 최종 업데이트: 2026-07-06 | MySQL 8.4 / InnoDB 기준

## 개념

인덱스는 테이블의 특정 컬럼을 **미리 정렬해 둔 별도의 탐색용 자료구조**다. 원하는 행을 찾을 때 테이블 전체를 훑지(풀 스캔) 않고, 정렬된 인덱스에서 곧바로 위치를 찾아간다.

> 책 뒤편의 "찾아보기(색인)"와 같다. "트랜잭션"이라는 단어를 찾으려 책을 처음부터 넘기는 대신(풀 스캔), 색인에서 단어 → 페이지를 바로 찾는다(인덱스 스캔).

인덱스는 공짜가 아니다. **조회는 빨라지지만, 쓰기는 느려진다** — INSERT/UPDATE/DELETE마다 관련 인덱스도 함께 갱신해야 하고, 저장 공간도 더 쓴다. 그래서 "무조건 많이"가 아니라 **자주 조회되는 컬럼에 선별적으로** 건다.

| 항목 | 인덱스 없음 | 인덱스 있음 |
|------|-------------|-------------|
| 조회 | 풀 스캔 O(n) | B-Tree 탐색 O(log n) |
| 쓰기 | 빠름 | 인덱스 갱신 비용 추가 |
| 저장 공간 | — | 인덱스만큼 추가 |

## B-Tree 구조와 인덱스 갱신

InnoDB는 인덱스를 **B-Tree**(정확히는 B+Tree) 구조로 관리한다. 정렬된 다단계 트리라 등호 검색뿐 아니라 **범위 검색·정렬(ORDER BY)**에도 강하고, 탐색이 `O(log n)`이다.

새 행을 INSERT하면 그 행이 포함된 **모든 인덱스가 함께 갱신**된다.

1. **위치 탐색** — 삽입할 값이 인덱스의 어느 위치에 들어갈지 결정
2. **페이지 갱신** — 해당 위치에 엔트리 추가. 페이지가 꽉 차면 **페이지 분할(split)** 발생
3. **구조 조정** — 분할·병합이 일어나면 상위 노드까지 갱신

인덱스가 많을수록 이 갱신 비용이 누적되므로, 쓰기가 잦은 테이블은 인덱스 개수에 신중해야 한다.

## 클러스터형 인덱스 vs 세컨더리 인덱스

InnoDB에서 반드시 알아야 할 구분이다.

| 구분 | 클러스터형 인덱스 | 세컨더리(보조) 인덱스 |
|------|-------------------|------------------------|
| 대상 | **기본키(PK)** | 그 외 일반 인덱스 |
| 저장 방식 | **데이터 행 자체가 PK 순으로 정렬 저장** | 리프에 인덱스 컬럼 + **PK 값**만 저장 |
| 개수 | 테이블당 1개 | 여러 개 |

> 클러스터형은 **사전(dictionary)**과 같다. 단어(PK)가 곧 본문 순서라, 단어를 찾으면 뜻(행 데이터)이 바로 거기 있다. 세컨더리 인덱스는 **책 뒤 색인**이라, 단어 → 페이지 번호(PK)만 알려주고, 실제 내용은 그 페이지로 다시 가야 본다.

이 "다시 가는" 동작이 핵심이다. 세컨더리 인덱스로 조회하면 리프에서 PK를 얻은 뒤, **클러스터형 인덱스를 한 번 더 타고 실제 행**을 읽는다(북마크 룩업 / 테이블 back).

```mermaid
graph LR
    A["email 인덱스 검색"] --> B["리프에서 PK 획득"]
    B --> C["PK로 클러스터형 인덱스 재조회"]
    C --> D["실제 행 데이터"]
```

이 2단계 비용은 **커버링 인덱스**로 없앨 수 있다(아래 참고).

## 선택도와 카디널리티

인덱스 효율을 가늠하는 두 지표인데, 사실상 같은 것을 다른 각도로 본 것이다.

| 용어 | 정의 | 예 |
|------|------|-----|
| **카디널리티** | 컬럼의 **고유 값 개수**(절대 수) | `email`: 100만, `성별`: 2 |
| **선택도** | 카디널리티 / 전체 행 수 (비율, `0 < 값 ≤ 1`) | `email` ≈ 1.0, `성별` ≈ 0.000002 |

**둘 다 높을수록(1에 가까울수록) 인덱스가 효율적**이다. 고유 값이 많아야 조건 하나로 검색 범위를 확 좁힐 수 있기 때문이다. 주민번호·이메일은 높고(좋은 인덱스 후보), 성별·상태코드는 낮다(단독 인덱스 효과 미미).

```sql
-- 선택도 = 고유 값 수 / 전체 행 수
SELECT COUNT(DISTINCT MB_ID) / COUNT(*) AS selectivity FROM TMG_MSG_GRP;
```

카디널리티는 `SHOW INDEX`로 확인한다. 단 이 값은 **근사치**라, 데이터가 많이 바뀌면 `ANALYZE TABLE`로 통계를 갱신해야 옵티마이저가 정확히 판단한다.

```sql
SHOW INDEX FROM TMG_MSG_GRP;   -- Cardinality 컬럼 확인
ANALYZE TABLE TMG_MSG_GRP;     -- 통계 갱신
```

| SHOW INDEX 주요 컬럼 | 의미 |
|----------------------|------|
| `Key_name` | 인덱스 이름 |
| `Seq_in_index` | 복합 인덱스 내 컬럼 순서 |
| `Column_name` | 인덱스 컬럼 |
| `Cardinality` | 고유 값 수 근사치 |
| `Non_unique` | 0=유니크, 1=중복 허용 |

> ⚠️ 카디널리티가 높아도 **데이터 분포가 치우치면**(특정 값에 몰림) 실제 효율은 떨어질 수 있다. MySQL 8.0+는 이를 보완하는 **히스토그램**(`ANALYZE TABLE ... UPDATE HISTOGRAM ON col`)을 지원한다.

## 복합 인덱스와 왼쪽 프리픽스 (Leftmost Prefix)

두 개 이상의 컬럼으로 만든 인덱스가 **복합 인덱스**다. 여기엔 결정적인 규칙이 있다 — **왼쪽 컬럼부터 연속으로 조건에 써야만 인덱스를 탄다.**

### 왜 그런가 — 정렬 원리

복합 인덱스 `(A, B, C)`는 이렇게 정렬돼 저장된다.

> **A로 먼저 정렬 → 같은 A 안에서 B로 정렬 → 같은 B 안에서 C로 정렬**

즉 B와 C는 **"A가 같다"는 전제 안에서만** 정렬돼 있다. A가 빠지면 B는 인덱스 전체에 흩어져 있어 못 찾는다.

> 전화번호부가 `(성, 이름)` 순인 것과 같다. "김"씨 찾기(성)와 "김철수" 찾기(성+이름)는 쉽지만, 이름이 "철수"인 사람은 성을 모르면 처음부터 다 뒤져야 한다. 이름은 **성 안에서만** 정렬돼 있기 때문이다.

### 인덱스 `(A, B, C)` — 어떤 쿼리가 타나

| WHERE 조건 | 인덱스 활용 | 이유 |
|-----------|------------|------|
| `A = ?` | ✅ 탐 | 왼쪽부터 |
| `A = ? AND B = ?` | ✅ 탐 | A, B 연속 |
| `A = ? AND B = ? AND C = ?` | ✅ 완전 활용 | 전체 |
| `B = ?` | ❌ 못 탐 | A를 건너뜀 |
| `B = ? AND C = ?` | ❌ 못 탐 | A가 없음 |
| `A = ? AND C = ?` | ⚠️ **A만** 탐 | B가 없어 C는 못 씀 |

마지막 줄이 핵심이다. A와 C가 있어도 **중간의 B가 빠지면 C는 인덱스를 못 탄다.** C는 B가 정해져야 정렬되기 때문이다.

### 함정: 범위 조건이 오면 거기서 끊긴다

등호(`=`)가 아니라 **범위 조건**(`>`, `<`, `BETWEEN`, `LIKE 'x%'`)이 중간에 오면, **그 컬럼까지만** 인덱스를 타고 뒤는 못 탄다.

```sql
-- 인덱스 (A, B, C)
WHERE A = 1 AND B > 10 AND C = 5
--    A(=) ✅   B(범위)까지만 ✅   C ❌ (B가 범위라 C는 정렬이 깨짐)
```

**왜 끊기나** — C는 "B가 같은 값일 때만" 정렬돼 있기 때문이다. 등호는 B를 하나로 고정하지만, 범위는 B를 여러 값으로 벌려 C를 흩어놓는다. 아래는 인덱스 `(A, B, C)`의 `A=1` 부분이 저장된 순서다.

| A | B | C |
|---|---|---|
| 1 | 10 | 3 |
| 1 | 20 | 2 |
| 1 | 20 | **5** |
| 1 | 30 | 1 |
| 1 | 30 | **5** |
| 1 | 30 | 9 |

- `B = 20 AND C = 5` (등호) → B=20은 **연속된 한 덩어리**라 그 안에서 C=5를 바로 찾는다. ✅
- `B > 10 AND C = 5` (범위) → C=5가 B=20 구간과 B=30 구간에 **흩어져** 있어, C로 점프하지 못하고 구간을 훑으며 걸러내야 한다. ❌

정확히는 범위 컬럼(B)까지는 인덱스로 좁히고(range scan), 그 뒤 컬럼(C)부터는 정렬을 못 써 필터링만 한다(`EXPLAIN`의 `Using index condition`).

그래서 **범위 조건 컬럼은 복합 인덱스에서 되도록 뒤쪽**에 둔다.

### 복합 PK도 동일하다

복합 기본키도 내부적으로 복합 인덱스라 같은 규칙을 따른다.

```sql
PRIMARY KEY (member_id, product_id)

WHERE member_id = 1                      -- ✅ 탐 (왼쪽)
WHERE member_id = 1 AND product_id = 9   -- ✅ 탐
WHERE product_id = 9                     -- ❌ 못 탐 (왼쪽 member_id 없음)
```

## 복합 인덱스 컬럼 순서 설계

위 규칙에서 자연스럽게 설계 원칙이 나온다.

1. **동등 조건(`=`, `IN`) 컬럼을 선두**에 배치 — 검색 범위를 정확히 좁힌다.
2. 동등 조건 컬럼끼리는 **선택도가 높은 순**으로 (단, 등호끼리는 성능 차가 크지 않다).
3. **범위 조건 컬럼은 그 뒤**에 — 범위 이후 컬럼은 인덱스를 못 타므로.
4. `ORDER BY`/`GROUP BY`에 쓰는 컬럼도 인덱스 순서에 맞추면 정렬을 생략할 수 있다.

```sql
-- 쿼리: MB_ID·MSG_DVS_CD는 등호, REG_DTT는 범위
SELECT COUNT(*) FROM TMG_MSG_GRP
WHERE MB_ID = ? AND MSG_DVS_CD = ? AND API_INSTC_ID IS NULL AND REG_DTT >= ?;

-- 인덱스: 등호 컬럼 먼저, 범위(REG_DTT) 마지막
CREATE INDEX idx_tmg_msg_grp_opt
  ON TMG_MSG_GRP (MB_ID, MSG_DVS_CD, API_INSTC_ID, REG_DTT);
```

> 참고로 **WHERE 절에 쓴 조건의 순서**는 성능과 무관하다. 옵티마이저가 인덱스·선택도·비용을 따져 조건을 **자동 재배열**하기 때문이다. 개발자는 WHERE 순서가 아니라 **인덱스 설계**에 집중하면 된다. (`A=? AND B=?`나 `B=? AND A=?`나 동일)

## 커버링 인덱스 (Covering Index)

쿼리가 필요로 하는 **모든 컬럼이 인덱스 안에 있으면**, 클러스터형 인덱스로 되돌아가지 않고 **인덱스만 읽어** 결과를 낸다. 앞서 본 세컨더리 인덱스의 2단계 조회(북마크 룩업)를 통째로 없애 매우 빠르다.

```sql
CREATE INDEX idx_cover ON orders (user_id, status, amount);

-- user_id, status, amount가 전부 인덱스에 있음 → 테이블 접근 없음
SELECT amount FROM orders WHERE user_id = 1 AND status = 'PAID';
```

`EXPLAIN` 결과 `Extra`에 **`Using index`**가 뜨면 커버링 인덱스가 적용된 것이다.

## 단일 인덱스 여러 개 vs 복합 인덱스

WHERE에 쓰이는 컬럼마다 **단일 인덱스**를 따로 두면, MySQL은 대개 그중 **하나만** 선택해 쓴다(선택도가 가장 높은 것). 나머지 조건은 인덱스로 걸러진 행에 대해 추가 필터링된다.

**인덱스 머지(Index Merge)**로 여러 단일 인덱스를 조합하기도 한다.

| 머지 유형 | 동작 |
|-----------|------|
| UNION | 여러 인덱스 결과의 합집합 (`OR` 조건) |
| INTERSECTION | 교집합 (`AND` 조건) |
| UNION + INTERSECTION | 둘의 조합 |

하지만 인덱스 머지는 병합 오버헤드가 있어 **복합 인덱스보다 느린 경우가 많다.** 자주 함께 쓰이는 컬럼은 **복합 인덱스 하나**로 만드는 게 낫다. `EXPLAIN`에 `Using index merge`가 보이는데 성능이 아쉽다면 복합 인덱스를 검토한다.

> 옵티마이저가 복합 인덱스를 두고도 단일 인덱스를 고르는 경우가 있다 — 복합 인덱스의 **선두 컬럼 선택도가 낮으면**, 그 인덱스를 타도 범위를 못 좁힌다고 판단해 비용상 다른 선택을 한다. 선두 컬럼 선택도가 중요한 이유다.

## 운영 중 인덱스 추가

이미 서비스 중인 대용량 테이블에 인덱스를 거는 건 조심스럽다. 인덱스 생성이 테이블을 오래 잠그면 장애로 이어진다.

- **ONLINE DDL** — MySQL 8.x는 대부분의 인덱스 추가를 `ALGORITHM=INPLACE, LOCK=NONE`으로 온라인 처리해, 읽기/쓰기를 막지 않고 생성한다.
  ```sql
  ALTER TABLE orders ADD INDEX idx_user (user_id), ALGORITHM=INPLACE, LOCK=NONE;
  ```
- 그래도 대형 테이블은 부하가 크므로 **트래픽이 적은 시간대**에, 필요하면 `pt-online-schema-change`·`gh-ost` 같은 무중단 스키마 변경 도구를 쓴다.
- 추가 전후로 `EXPLAIN`으로 실제 인덱스 사용 여부를 확인한다. MySQL 8.0+의 **인비저블 인덱스**(`INVISIBLE`)로 삭제 전 영향도를 안전하게 테스트할 수 있다.

## 결론

1. 동등 조건(`=`) 컬럼을 인덱스 **선두**에 둔다.
2. 그중 **선택도 높은 컬럼**부터 배치한다.
3. **범위 조건** 컬럼은 그 **뒤**에 둔다.
4. 가능하면 조회 컬럼까지 담아 **커버링 인덱스**로 만든다.
5. 쓰기 비용·중복 인덱스를 고려해 **최소한**으로 유지한다.
