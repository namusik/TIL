# 레이턴시 백분위와 히스토그램

> 최종 업데이트: 2026-07-29 | 성능 측정 관점

## 개념

응답시간(레이턴시)을 하나의 숫자로 요약할 때 **무엇으로 요약하느냐**가 성능 판단을 좌우한다. 흔히 쓰는 **평균**은 느린 소수를 숨기므로, 실무는 **백분위(p95·p99)**로 성능을 판단하고, 그 백분위를 재기 위해 **히스토그램**을 수집한다.

> 시험 성적으로 비유하면 — **평균 점수**만으로는 "하위권이 몇 점인지" 모른다. **성적 분포표(히스토그램)**가 있어야 "하위 5% 커트라인(=백분위)"을 알 수 있다.

## 왜 평균은 위험한가 — 꼬리를 숨긴다

로그인 요청 100건 중 99건이 10ms, 1건이 5000ms라고 하자.

- **평균** ≈ 60ms → "빠르다"고 오판
- 하지만 **그 1명은 5초를 기다렸다**

평균은 이런 **느린 꼬리(tail)**를 극단값 몇 개에 가려 못 본다. 사용자 불만은 평균이 아니라 이 꼬리에서 터진다.

## 백분위 (Percentile)

**요청의 N%가 이 값 이하**임을 나타낸다. 꼬리를 직접 겨냥한다.

| 지표 | 의미 |
|------|------|
| **p50 (중앙값)** | 절반이 이 값 이하 — 전형적 경험 |
| **p95** | 95%가 이 값 이하 — 느린 상위 5%의 경계 |
| **p99** | 99%가 이 값 이하 — 가장 느린 1%가 겪는 지연 |
| **p99.9** | 대규모 트래픽에서 중요 — 극단 꼬리 |

> 놀이공원 대기시간과 같다. "평균 20분"이라도 **p99 = 100명 중 가장 오래 기다린 순서로 99등의 대기시간**이다.

**왜 p99가 사용자 경험을 지배하나** — 한 화면이 내부적으로 여러 API·백엔드 호출을 부르면, **그중 하나만 꼬리에 걸려도 전체가 느려진다.** 요청이 많아질수록 사용자가 꼬리를 만날 확률이 커지므로, 평균이 좋아도 p99가 나쁘면 체감은 느리다. (Google "The Tail at Scale")

## 백분위를 어떻게 재나 — 히스토그램

정확한 p95를 내려면 **모든 요청의 응답시간을 정렬**해 95% 지점을 찾아야 한다. 그런데 초당 수천·수만 요청의 값을 전부 저장·정렬하는 건 너무 비싸다.

그래서 **미리 정한 구간(bucket)에 몇 건이 들어갔는지 개수만 센다** — 이것이 히스토그램이다.

## 히스토그램 버킷

응답시간을 구간별로 나눠, 각 구간에 몇 건이 들어갔는지 세는 **누적 카운터**다.

| 버킷 (이하) | 누적 개수 (100건 중) |
|-------------|----------------------|
| ≤10ms | 40 |
| ≤25ms | 75 |
| ≤50ms | **95** → p95 |
| ≤100ms | **99** → p99 |
| ≤250ms | 100 |

**버킷은 백분위 계산의 원재료다.** 전체 100건 중 95건이 `≤50ms`까지 채워지므로 **p95 ≈ 50ms**, 99건이 `≤100ms`까지이므로 **p99 ≈ 100ms**다. 버킷이 없으면 이 계산 자체가 불가능하다 — **분포표 없이 커트라인을 못 긋는 것**과 같다.

## 구현 (Prometheus + Micrometer)

**Prometheus 히스토그램**은 세 가지를 노출한다.

| 메트릭 | 내용 |
|--------|------|
| `_bucket{le="0.05"}` | 각 구간(≤50ms 등)까지의 **누적 개수** |
| `_sum` | 전체 응답시간 합 |
| `_count` | 전체 건수 |

`_sum / _count`로 평균을, `histogram_quantile(0.95, ...)`로 **p95를 근사**한다.

**Micrometer(Spring)** 의 Timer는 기본적으로 **count·sum·max만** 수집한다. 버킷은 **명시적으로 켜야** 생긴다.

```yaml
# 이걸 안 켜면 버킷이 없어 → 백분위를 못 잰다
management:
  metrics:
    distribution:
      percentiles-histogram:
        http.server.requests: true      # 히스토그램 버킷 활성화
      slo:
        http.server.requests: 50ms,100ms,200ms   # 관심 버킷 경계 지정(선택)
```

### 특정 엔드포인트에만 선별 활성화

위 프로퍼티는 **메트릭 이름 단위**라 URI별로는 안 된다. 특정 path만 켜려면 두 방법이 있다.

**① MeterFilter — 기존 `http.server.requests`의 특정 uri만**
```java
@Bean
MeterFilter loginHistogram() {
    return new MeterFilter() {
        @Override
        public DistributionStatisticConfig configure(Meter.Id id, DistributionStatisticConfig config) {
            if ("http.server.requests".equals(id.getName())
                    && "/api/login".equals(id.getTag("uri"))) {   // 이 path만
                return DistributionStatisticConfig.builder()
                        .percentilesHistogram(true)
                        .build().merge(config);
            }
            return config;   // 나머지는 평균만
        }
    };
}
```

**② @Timed — 특정 메서드에 전용 지표** (`TimedAspect` 빈 필요)
```java
@Timed(value = "login.requests", histogram = true, percentiles = {0.95, 0.99})
@PostMapping("/api/login")
public ResponseEntity<?> login(...) { ... }
```

> ⚠️ **왜 전역이 아니라 선별인가** — 히스토그램은 **버킷 수만큼 시계열이 늘어난다.** 전역으로 켜면 `모든 URI × 모든 버킷`으로 **카디널리티가 폭증**해 Prometheus 저장·쿼리 비용이 급증한다. 그래서 로그인·결제처럼 **SLO가 중요한 소수 엔드포인트에만** 켜는 게 정석이다. ([Loki](../DevOps/로깅-서비스/Loki.md)에서 고cardinality 라벨을 피하는 것과 같은 이유 — 측정도 공짜가 아니다.)

## ⚠️ 백분위는 평균 낼 수 없다 — 히스토그램이 중요한 또 다른 이유

여러 서버 인스턴스의 **p95를 산술평균 내면 틀린 값**이다. "인스턴스 A의 p95 40ms, B의 p95 60ms → 평균 50ms"는 전체 p95가 아니다. 백분위는 **더할 수 없는(non-additive)** 값이기 때문이다.

**히스토그램 버킷은 더할 수 있다.** 여러 인스턴스·여러 시간대의 버킷 카운트를 **합산한 뒤** quantile을 계산해야 올바른 전체 p95가 나온다. 이 **집계 가능성(aggregatable)**이 히스토그램을 쓰는 또 다른 핵심 이유다.

> 그래서 Prometheus에서 **Histogram**(버킷을 서버가 수집, quantile은 쿼리 시 계산 → 집계 가능)이 **Summary**(앱이 quantile을 미리 계산 → 집계 불가)보다 다중 인스턴스 환경에서 선호된다.
