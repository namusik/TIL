# ISO 8601 — 날짜·시간 표기

> 최종 업데이트: 2026-06-23 | ISO 8601-1:2019 · RFC 3339 기준

## 개념

**ISO 8601** 은 날짜와 시간을 **문자열로 명확하게 표현하는 국제 표준**이다. `2024-05-15T00:00:00.000+09:00` 처럼 생긴 그 표기가 전부 이 규격이다. 핵심 목적은 **언어·지역·시스템이 달라도 같은 순간을 똑같이 읽게** 만드는 것이다.

> 비유: 나라마다 "5/15", "15/5", "May 15"로 제각각 쓰면 `03/04`가 3월 4일인지 4월 3일인지 싸움이 난다. ISO 8601은 "**큰 단위→작은 단위 순서로, 정해진 모양으로만 쓰자**"는 전 세계 공통 약속이다.

규칙은 단순하다 — **연 → 월 → 일 → 시 → 분 → 초** 순으로, 큰 단위를 앞에 둔다. 그래서 문자열을 그냥 정렬해도 시간순 정렬이 된다(사전순 = 시간순).

## 형식 뜯어보기

`2024-05-15T00:00:00.000+09:00` 한 줄을 조각내면 이렇다.

```
2024-05-15 T 00:00:00.000 +09:00
└─날짜──┘ │ └──시각────┘     └오프셋┘
          └ 날짜·시각 구분자
```

| 조각 | 의미 |
|------|------|
| `2024-05-15` | 날짜 — **YYYY-MM-DD** (연-월-일) |
| `T` | 날짜와 시각을 가르는 **구분 문자** ("여기부터 시간") |
| `00:00:00` | 시각 — **시:분:초** (24시간제) |
| `.000` | 밀리초(소수 초). 생략 가능, 자리수는 구현마다 다름 |
| `+09:00` | **UTC 오프셋** — 이 시각의 시간대 |

## 타임존 오프셋 — 가장 중요한 꼬리

맨 끝의 `+09:00`이 ISO 8601의 핵심이다. **"이 시각이 어느 시간대 기준이냐"** 를 못 박는 **오프셋(offset)** 이다. 세계 표준시 **UTC**(영국 그리니치 기준)로부터 몇 시간 차이인지를 적는다. 한국(KST)은 UTC보다 9시간 빠르므로 `+09:00`.

```
2024-05-15T00:00:00+09:00   ← 한국 자정
2024-05-14T15:00:00Z        ← 같은 순간을 UTC로 표기 (Z = +00:00)
```

- **`Z`** : "Zulu time"이라 읽고 **UTC(+00:00)** 를 뜻한다. `+00:00`과 같다
- **`+09:00` / `-05:00`** : UTC 기준 앞선/뒤처진 시간. 동쪽이 `+`, 서쪽이 `-`

> 비유: "3시에 만나자"는 어느 도시 3시인지 모르면 어긋난다. `+09:00`은 "서울 시계로 3시"라고 도시를 못 박는 꼬리표다. 이게 빠지면 같은 `00:00:00`이 서버마다 9시간씩 틀어진다.

## 배경/역사

| 시기 | 내용 |
|------|------|
| 1988 | **ISO 8601** 최초 발행 — 국가마다 다르던 날짜 표기를 통일 |
| 2002 | **RFC 3339** 발행 — 인터넷용으로 ISO 8601을 좁혀 규정 (Klyne·Newman) |
| 2019 | **ISO 8601-1:2019 / -2:2019** 로 개정 (기본 규칙 + 확장 분리) |

**ISO 8601 ⊃ RFC 3339** 관계로 보면 된다. ISO 8601은 폭넓은 표기를 허용하고, RFC 3339는 그중 인터넷에서 안전한 부분집합만 엄격히 못 박았다. API·로그·DB에서 보는 형식은 대개 RFC 3339 쪽이다.

## 자주 보는 변형들

날짜·시각·기간 등을 부분적으로도 표기할 수 있다.

| 표기 | 의미 |
|------|------|
| `2024-05-15` | 날짜만 (시각·타임존 없음) |
| `2024-05` / `2024` | 월까지 / 연까지만 |
| `00:00:00` | 시각만 |
| `2024-05-15T09:30:00Z` | 날짜+시각+UTC |
| `2024-W20-3` | **주차 표기** — 2024년 20번째 주의 3일째(수) |
| `P3Y6M4DT12H30M5S` | **기간(duration)** — 3년 6개월 4일 12시간 30분 5초. `P`로 시작, `T` 뒤가 시간 |
| `2024-05-15/2024-05-20` | **구간(interval)** — 시작/끝을 `/`로 |

## 주의 — 실무 사고가 나는 지점

**1) `+09` vs `+0900` vs `+09:00`** — 오프셋 표기에서 가장 헷갈리는 지점이다. **ISO 8601은 세 형태를 모두 허용**한다.

| 형태 | 이름 | 예시 |
|------|------|------|
| `±hh` | 시간만(hours-only) | `+09` |
| `±hhmm` | 기본형(basic) | `+0900` |
| `±hh:mm` | 확장형(extended) | `+09:00` |

단 ISO 8601엔 **"한 표현 안에서 기본형과 확장형을 섞지 마라"** 는 일관성 규칙이 있다. 날짜·시각을 확장형(`2024-05-15T00:00:00`, 콜론 있음)으로 썼으면 오프셋도 **확장 계열(`±hh:mm` 또는 콜론이 없는 `±hh`)** 로 맞춰야 하고, 기본형 `±hhmm`을 섞으면 위반이다. 자바 21 `OffsetDateTime.parse` 실측이 이 규칙을 그대로 따른다.

```
2024-05-15T00:00:00+09:00   ✅ 확장형 + 확장형
2024-05-15T00:00:00+09      ✅ 확장형 + 시간만(콜론 충돌 없음)
2024-05-15T00:00:00+0900    ❌ 확장형 날짜에 기본형 오프셋 섞음 → DateTimeParseException
2024-05-15T00:00:00Z        ✅ UTC
20240515T000000+0900        ✅ 기본형 + 기본형 (날짜·시각·오프셋 모두 구분자 생략 — 짝이 맞음)
```

마지막 줄이 핵심이다 — **`+0900`(기본형 오프셋) 자체가 틀린 게 아니라, 확장형 날짜에 섞어서 틀린 것**이다. 날짜·시각까지 기본형(`20240515T000000`, 하이픈·콜론 없음)으로 통일하면 `+0900`도 valid하다. 단 자바의 기본 ISO 파서(`OffsetDateTime.parse(str)`)는 **확장형만** 받으므로, 기본형 전체를 파싱하려면 커스텀 패턴(`yyyyMMdd'T'HHmmssXX`)을 직접 지정해야 한다.

즉 `+09`는 표준 위반이 아니고 자바 기본 파서도 받는다 — 오히려 확장형 날짜에 분까지 붙인 `+0900`을 섞으면 깨진다. 다만 **RFC 3339(인터넷 표준)는 `+09:00` 풀형만** 인정하므로, 받는 쪽이 RFC 3339 잣대면 `+09`도 거부될 수 있다. 그래서 어디서도 안 깨지는 안전지대는 여전히 **`+09:00`** 이다.

**2) 타임존 없는 표기(naive)** — `2024-05-15T00:00:00` 처럼 오프셋이 없으면 "어느 시간대인지 모르는 시각"이다. 이걸 그대로 저장·전송하면 읽는 쪽이 제멋대로 해석해 **9시간씩 틀어지는 사고**가 난다. 시점(instant)을 다룰 땐 **항상 오프셋을 붙이거나, UTC로 저장**하는 게 원칙이다 ([DB 타임존](../../Database/MySQL/MySQL-날짜시간-저장.md) 참고).

**3) 자바 타입 대응** — 이 형식은 `java.time` 타입과 1:1로 맞물린다.

```java
// 오프셋 있음 → 정확한 "시점"
OffsetDateTime.parse("2024-05-15T00:00:00+09:00");   // 오프셋까지 보존
Instant.parse("2024-05-14T15:00:00Z");               // UTC 절대 시점

// 오프셋 없음 → "벽시계 값"일 뿐, 시점 아님
LocalDateTime.parse("2024-05-15T00:00:00");          // 타임존 정보 없음
```

`java.time`의 기본 포맷이 곧 ISO 8601이라, `toString()`만 해도 이 형식으로 나온다.
