# 암호학적 해시와 비밀번호 해싱

> 최종 업데이트: 2026-07-29 | 보안 관점

## 개념

암호학적 해시는 데이터의 **고유 지문(단방향 요약)** 을 만드는 것이다. 자료구조용 해시([해싱 — 해시 테이블](../알고리즘/Hashing.md))와 원리는 같지만, 보안에서는 **단방향성**(원본 역산 불가)과 **충돌 저항성**(같은 해시를 일부러 만들기 어려움)이 반드시 필요하다.

| 용도 | 동작 |
|------|------|
| **비밀번호 저장** | 평문 대신 해시값만 저장. 로그인 시 입력값을 해시해 비교 → DB가 새도 원본 비번을 모름 |
| **무결성 검증** | 파일의 SHA-256 체크섬 비교로 변조·손상을 잡아냄 |
| **디지털 서명·인증서** | 원문 대신 해시에 서명 |
| **식별자** | Git 커밋 해시, 블록체인 블록 해시 |

```java
// 무결성용 해시 (빠른 암호학적 해시)
byte[] digest = MessageDigest.getInstance("SHA-256").digest(fileBytes);
```

## 암호화(Encryption) ≠ 해싱

가장 자주 헷갈리는 지점이다. 둘 다 데이터를 알아볼 수 없게 바꾸지만 **방향이 정반대**다.

| | 암호화 | 해싱 |
|---|--------|------|
| 방향 | **양방향** — 키로 복호화해 원문 복원 | **단방향** — 복원 불가 |
| 목적 | 비밀 유지 후 **다시 읽기** | **지문·검증** (다시 읽을 필요 없음) |
| 예 | AES, RSA | SHA-256, bcrypt |

→ **비밀번호는 "암호화"가 아니라 "해싱"해서 저장하는 게 정석**이다. 서버조차 원본 비번을 알 필요가 없기 때문이다.

## 비밀번호 해싱 — 실무 규칙

단순히 SHA-256으로 한 번 돌리는 것으로는 부족하다. 두 가지가 핵심이다.

- **솔트(salt)**: 사용자마다 무작위값을 섞어 해싱한다. 같은 비번이라도 해시가 전부 달라져, 미리 계산된 공격표(**레인보우 테이블**)를 무력화한다. **솔트는 비밀이 아니라서** 숨기지 않고 해시값과 함께 저장한다.
- **일부러 느린 함수**: 비번에는 SHA-256(너무 빠름) 대신 **bcrypt·scrypt·Argon2id**를 쓴다. 느려야 무차별 대입(브루트포스)이 비싸진다.

### bcrypt — 검증된 표준

```java
// Spring Security — 솔트·반복 비용이 내장된 bcrypt
var encoder = new BCryptPasswordEncoder();
String stored = encoder.encode(rawPassword);       // 솔트 자동 포함
boolean ok  = encoder.matches(rawPassword, stored); // 재해싱 후 비교
```

`encode()`는 호출할 때마다 **무작위 솔트를 자동 생성**해 결과 문자열에 박아 넣는다. 그래서 **회원 테이블에 별도 `salt` 컬럼을 만들 필요 없이** 이 문자열 한 줄만 저장하면 된다.

```
$2b$12$R9h/cIPz0gi.URNNX3kh2OPST9/PgBkqquzi.Ss7KIUgO2t0jWMUW
```

| 구획 | 값 | 의미 |
|------|-----|------|
| 버전 | `$2b$` | 알고리즘 버전 |
| cost | `12` | 반복 라운드(2^12) |
| 솔트 | 이어지는 22자 | 무작위 솔트(base64) |
| 해시 | 나머지 31자 | 실제 해시값 |

솔트가 매번 달라지므로 **같은 비번을 `encode()`해도 결과가 매번 다르다.** 따라서 검증은 `==`가 아니라 반드시 `matches()`로 한다 — 저장된 문자열에서 솔트를 꺼내 다시 해싱해 비교한다.

### 어떤 느린 해시를 쓸까 — 요즘은 Argon2id

느린 해시도 종류가 여럿이고, 현재 **OWASP 권장 1순위는 Argon2id**다.

| 함수 | 특징 | 위치 |
|------|------|------|
| PBKDF2 | CPU 비용만(메모리 안 씀). FIPS 승인 | 규제 필요 시 |
| **bcrypt** | 검증된 표준. 입력 72바이트 제한 | 여전히 무난 |
| scrypt | 메모리 하드 1세대 | — |
| **Argon2id** | 메모리 하드 + 사이드채널 방어 | ✅ 신규 권장 |

**Argon2**는 2015년 **PHC(Password Hashing Competition) 우승**, RFC 9106 표준이다. 차별점은 **메모리 하드(memory-hard)** — 계산에 메모리를 많이 써서, bcrypt·PBKDF2가 취약한 **GPU·ASIC 대량 크래킹을 막는다**(메모리는 병렬화가 비싸다). 변종이 셋이며(`d`=GPU 저항, `i`=사이드채널 저항, `id`=둘의 하이브리드) 실무는 **Argon2id**를 쓴다. 파라미터는 메모리(m)·반복(t)·병렬(p) 셋으로, OWASP는 `m=19MiB, t=2, p=1`을 출발점으로 권장한다.

```java
// Spring Security — Argon2id
var encoder = new Argon2PasswordEncoder(16, 32, 1, 19456, 2);
//                                     salt,hash,p,   m,   t
String stored = encoder.encode(rawPassword);
boolean ok = encoder.matches(rawPassword, stored);
```

bcrypt로도 충분하지만, **신규 프로젝트라면 Argon2id가 현재 권장**이다.

### 페퍼(pepper)

**페퍼**는 솔트와 반대로 **비밀**로 둔다. DB가 아닌 앱 설정·HSM 등 별도 위치의 전역 시크릿으로, DB만 털렸을 때의 추가 방어벽이다.

| | 솔트(salt) | 페퍼(pepper) |
|---|-----------|-------------|
| 범위 | 사용자마다 각각 | 앱 전체 공용 하나 |
| 비밀? | 공개(해시와 함께 저장) | 비밀(DB 아닌 별도 위치) |
| 목적 | 레인보우 무력화·해시 유니크화 | DB 유출 시 추가 방어 |

## 대표 해시 함수

| 함수 | 주 용도 | 상태 |
|------|---------|------|
| `hashCode()`, MurmurHash | 해시 테이블(비암호) | 속도용, 보안 강도 없음 |
| **MD5** | (과거 체크섬) | ❌ 2004 충돌 — 폐기 |
| **SHA-1** | (과거 서명) | ❌ 2017 SHAttered — 폐기 |
| **SHA-2** (SHA-256/512) | 무결성·서명 | ✅ 현재 표준 |
| **SHA-3** (Keccak) | 무결성 | ✅ 2015 FIPS 202 표준 |
| **bcrypt·scrypt·Argon2id** | 비밀번호 전용 | ✅ 느린 해시 (Argon2id 권장) |

핵심: **비암호용(속도)과 암호용(안전)을 절대 섞지 말 것.** 해시 테이블에 SHA-256은 과하고, 비밀번호에 `hashCode()`나 MD5는 위험하다.
