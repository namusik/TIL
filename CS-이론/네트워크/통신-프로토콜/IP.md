# IP — 인터넷 주소와 패킷 전달

> 최종 업데이트: 2026-06-23 | IPv4(RFC 791) · IPv6(RFC 8200) 기준

## 개념

**IP(Internet Protocol)** 는 데이터를 **목적지까지 어디로 보낼지(주소)와 어떤 경로로 보낼지(라우팅)** 를 책임지는 네트워크 계층(L3) 프로토콜이다. 인터넷의 모든 통신은 IP 주소를 향해 **패킷** 단위로 쪼개져 전달된다.

> 비유: 택배 송장 시스템이다. 모든 소포(패킷)에는 **받는 주소(목적지 IP)와 보내는 주소(출발지 IP)** 가 적힌 송장이 붙고, 여러 **중계소(라우터)** 를 거쳐 목적지로 배달된다. 단, IP는 "반드시 도착한다"를 보장하지 않는다 — 그건 등기우편([TCP](TCP.md))의 몫이다.

핵심은 IP가 **"배달은 하되 도착은 보장하지 않는"(best-effort)** 프로토콜이라는 점이다. 순서·유실·중복을 책임지지 않으며, 그 신뢰성은 위 계층의 TCP가 얹어 완성한다. 그래서 둘을 묶어 **TCP/IP**라 부른다 ([TCP-IP-Model](../네트워크-모델/TCP-IP-Model.md)).

## 배경/역사

| 시기 | 내용 |
|------|------|
| 1981 | **RFC 791** 로 **IPv4** 표준화 (Jon Postel, DARPA). 32비트 주소 |
| 1990년대 | 인터넷 폭증으로 **IPv4 주소 고갈** 우려 → NAT·CIDR로 수명 연장 |
| 1998 | **IPv6** 최초 규격(RFC 2460). 128비트 주소 |
| 2011 | IANA의 IPv4 최상위 주소 풀 **공식 고갈** |
| 2017 | IPv6 표준 갱신(**RFC 8200**). 현재 IPv4와 병행 사용 |

IPv4 주소는 약 **43억 개**(2³²)뿐이라 일찍 고갈됐다. 이를 **NAT**(사설↔공인 변환)와 **CIDR**(주소 효율 배분)로 버티는 한편, 근본 해결책으로 **IPv6**(2¹²⁸, 사실상 무한)가 나왔다.

## IP가 하는 일과 안 하는 일

| 구분 | 내용 |
|------|------|
| **하는 일** | 주소 지정(addressing), 경로 결정(routing), 패킷 분할·재조립 |
| **안 하는 일** | 도착 보장 ❌, 순서 보장 ❌, 중복 방지 ❌ |

→ 안 하는 일들은 전부 **TCP가 ACK·시퀀스·재전송으로 보완**한다. IP는 "일단 최선을 다해 보낸다"까지만 책임진다.

## IP 주소 체계

### IPv4 — 32비트

32비트를 **8비트씩 4덩이(옥텟)** 로 나눠 점으로 구분하고, 각 덩이를 0~255 십진수로 쓴다.

```
192.168.0.1
└─ 각 덩이(옥텟) = 8비트 = 0~255, 총 4덩이 = 32비트
```

### IPv6 — 128비트

128비트를 16비트씩 8덩이로 나눠 **16진수**와 콜론으로 쓴다. 주소가 사실상 무한해 고갈 문제가 없다.

```
2001:0db8:85a3:0000:0000:8a2e:0370:7334
연속된 0 묶음은 :: 로 축약 → 2001:db8:85a3::8a2e:370:7334
```

## 공인 IP vs 사설 IP

IP 주소는 **인터넷 전체에서 유일한 공인 IP**와, **내부망에서만 쓰는 사설 IP**로 나뉜다. 사설 대역은 **RFC 1918**로 예약돼 있다.

| 구분 | 범위 (실제 IP 범위) | 용도 |
|------|------------|------|
| **사설 (Private)** | `10.0.0.0/8` → `10.0.0.0` ~ `10.255.255.255` | 대규모 내부망 (기업·클라우드 VPC) |
| | `172.16.0.0/12` → `172.16.0.0` ~ `172.31.255.255` | 중간 규모 |
| | `192.168.0.0/16` → `192.168.0.0` ~ `192.168.255.255` | 가정·소규모 |
| **공인 (Public)** | 위 대역 외 전부 | 인터넷에서 직접 도달 가능 |

이 세 대역은 **RFC 1918로 고정**돼 있어 아무 숫자나 사설로 쓸 수 없다. 예컨대 `101.0.0.0`은 사설이 아니라 인터넷상의 **공인 IP**다.

> ⚠️ **흔한 함정 — "10·172·192로 시작하면 다 사설"이 아니다.** 첫 칸만 같다고 사설이 아니라 대역이 칼같이 정해져 있다.
> - **10**: 첫 칸이 10이면 전부 사설 ✅
> - **172**: 두 번째 칸이 **16~31일 때만** 사설. `172.15.x.x`·`172.32.x.x`는 **공인**
> - **192**: 두 번째 칸이 **168일 때만** 사설. `192.167.x.x`·`192.169.x.x`는 **공인**
>
> 그래서 `192.168.0.1`은 집 공유기에서 늘 보지만, `192.1.1.1`은 인터넷의 남의 주소다.

> 형님이 본 로그로 보면 — `10.40.159.217`은 **사설 IP**(10 대역, 사내·VPC 내부 서버)이고, `210.206.88.80`은 **공인 IP**(인터넷상의 상대 서버)다. 사내 서버가 사설 IP를 쓰는 이유가 이 RFC 1918 대역이다.

### NAT — 사설이 인터넷으로 나가는 법

사설 IP는 인터넷에서 직접 못 쓴다. 그래서 외부로 나갈 때 **NAT(Network Address Translation)** 가 사설 IP를 공인 IP로 **변환**한다. IPv4 고갈을 늦춘 핵심 기술이다.

> 비유: 회사 대표 전화번호(공인 IP) 하나로 수많은 내선(사설 IP)이 외부와 통화하는 것. 나갈 땐 대표번호로 보이고, 들어온 응답은 교환원(NAT)이 알맞은 내선으로 연결한다.

#### 세션 테이블 — 돌아올 응답을 짝지어 기억하는 표

NAT가 나가는 패킷의 출발지를 공인 IP로 덮어쓰면, 돌아온 응답만 봐서는 **원래 어느 사설 호스트 것이었는지 알 수 없다.** 그래서 NAT는 내보낼 때마다 **"누가 → 어디로 나갔다"는 매핑을 표에 기록**해두는데, 이게 **세션 테이블**(NAT translation table / connection tracking table, 리눅스에선 `conntrack`)이다. 응답이 오면 이 표를 뒤져 원래 사설 IP·포트로 **역변환**해 돌려준다.

```
내부(사설)             공인(변환 후)        목적지                프로토콜
10.40.159.217:51000 → 210.x.x.x:40001 → 210.206.88.80:443   TCP
10.40.159.218:52344 → 210.x.x.x:40002 → 8.8.8.8:53          UDP
```

핵심은 **포트까지 함께 기록**한다는 점이다. 공인 IP는 하나뿐인데 내부 호스트는 다수이므로, 포트 번호로 구분한다. 이렇게 포트까지 변환해 하나의 공인 IP를 공유하는 방식을 **PAT(Port Address Translation)** 또는 **NAPT**라 부른다. "대표번호 하나로 여러 내선"이 가능한 게 이 포트 구분 덕이다.

세션 테이블의 각 엔트리는 메모리가 유한하므로 **일정 시간 트래픽이 없으면(idle) 타이머가 만료되며 삭제**된다. 이 idle 만료가 오래 열어두는 TCP 연결(커넥션 풀 등)을 말없이 끊는 원인이 되는데, 이 실무 이슈는 [방화벽](../방화벽.md) 문서에서 다룬다.

> NAT가 L3에서 출발지 IP를 **덮어쓰는** 것과 달리, HTTP(L7)에서는 프록시가 원래 클라이언트 IP를 **X-Forwarded-For** 헤더에 **적어서** 전달한다. 로드밸런서 뒤에서 실제 클라이언트 IP를 얻는 방법(과 위조 방어)은 → [HTTP — 프록시와 클라이언트 IP](HTTP/HTTP.md).

### 특수 주소

| 주소 | 의미 |
|------|------|
| `127.0.0.1` | **루프백** — 자기 자신 (localhost) |
| `0.0.0.0` | "모든 주소" / 미지정 (서버가 전체 인터페이스 listen) |
| `255.255.255.255` | 브로드캐스트 (같은 망 전체) |

## 서브넷과 CIDR

하나의 IP 주소는 **네트워크 부분 + 호스트 부분**으로 나뉜다. 어디까지가 네트워크인지를 **서브넷 마스크**가 정하고, 이를 간결히 쓴 게 **CIDR 표기**다.

### 왜 네트워크 / 호스트로 나누나

전 세계 IP가 약 43억 개인데, 구분이 없다면 라우터는 **개별 주소를 전부 외워** 일일이 길을 판단해야 한다 — 불가능하다. 그래서 주소를 **앞부분(네트워크) + 뒷부분(호스트)** 으로 쪼개고, 라우터는 **네트워크 부분만 보고** "10.40.x.x로 시작하는 건 전부 저쪽 망으로" 한 줄로 처리한다. 수많은 주소를 한 줄로 압축하는 것이다.

> 비유: 우편 시스템이다. 집배원은 전국 모든 집 주소를 외우지 않는다. **우편번호(네트워크 부분)** 로 "이건 해운대구로" 큰 분류만 하고, 해운대 우체국에 도착한 뒤 **상세주소(호스트 부분)** 로 "몇 동 몇 호"를 찾는다.

둘은 쓰는 주체도 시점도 다르다.

| 구분 | 누가 쓰나 | 무슨 일에 쓰나 |
|------|----------|---------------|
| **네트워크 부분** | 라우터 (망과 망 사이) | "어느 **망**으로 보낼까" — 망 간 배달 |
| **호스트 부분** | 도착한 망의 스위치 | "그 망 안의 어느 **기기**냐" — 망 내 배달 |

가장 중요한 기능은 **"목적지가 내 망 안이냐 밖이냐"의 판단**이다. 호스트는 패킷을 보낼 때 서브넷 마스크로 내 네트워크 부분과 목적지의 네트워크 부분을 비교한다.

```
내 IP    : 192.168.0.10/24  → 네트워크 부분 = 192.168.0
목적지 A : 192.168.0.20      → 앞부분 같음 → "같은 망" → 직접 통신(ARP)
목적지 B : 10.40.159.7       → 앞부분 다름 → "딴 망"   → 게이트웨이로 떠넘김
```

- **네트워크 부분이 같으면** → 같은 LAN. 라우터 안 거치고 **직접 통신**
- **다르면** → 딴 망. 내 힘으로 못 가니 **게이트웨이(라우터)로 전달**

이 구분이 없으면 호스트는 패킷을 직접 보낼지 게이트웨이로 보낼지조차 정할 수 없다.

```
192.168.0.0/24
            └─ /24 = 앞 24비트가 네트워크 부분, 나머지 8비트가 호스트
               → 192.168.0.0 ~ 192.168.0.255 (256개 주소)
```

| CIDR | 네트워크 비트 | 호스트 수(대략) | 예 |
|------|-------------|----------------|-----|
| `/8` | 8 | 약 1,677만 | `10.0.0.0/8` |
| `/16` | 16 | 약 6.5만 | `192.168.0.0/16` |
| `/24` | 24 | 256 | `192.168.0.0/24` |
| `/32` | 32 | 1 (단일 호스트) | 방화벽에 IP 1개 지정 시 |

> 백엔드 실무에서 CIDR은 **VPC 서브넷 설계, 보안 그룹 규칙**에 그대로 쓰인다. 예를 들어 보안 그룹에 `10.40.0.0/16`을 허용하면 "10.40.x.x 사내망 전체"를, `/32`로 쓰면 "딱 그 IP 하나"를 뜻한다. 서브넷 심화는 [VPC 개념](../vpc-개념.md) 참고.

## IP 패킷 헤더 핵심 필드

모든 패킷 앞에는 IP 헤더가 붙는다. tcpdump로 보던 정보들이 여기서 나온다.

| 필드 | 역할 |
|------|------|
| **출발지 IP / 목적지 IP** | 누가 → 어디로 |
| **TTL** (Time To Live) | 라우터(홉)를 지날 때마다 1씩 감소. **0이 되면 폐기** → 무한 순환 방지 |
| **Protocol** | 상위 프로토콜 번호 (TCP=6, UDP=17, ICMP=1) |
| **Total Length** | 패킷 전체 크기 |

> TTL은 "소포가 너무 오래 떠돌면 폐기"하는 유통기한이다. 라우팅이 꼬여 패킷이 무한히 도는 걸 막는다. `traceroute`가 바로 이 TTL을 1씩 늘려가며 경로상의 라우터를 알아내는 도구다.

## 라우팅 — 패킷이 목적지를 찾아가는 법

IP 패킷은 한 번에 목적지로 가지 않고, **라우터(중계소)를 여러 번 거치며(홉, hop)** 전달된다. 각 라우터는 목적지 IP를 보고 **다음 홉**으로 넘긴다.

```mermaid
flowchart LR
    A[출발 호스트] --> G1[게이트웨이/라우터]
    G1 --> R1[라우터 1]
    R1 --> R2[라우터 2]
    R2 --> B[목적지 호스트]
```

- **게이트웨이**: 내 네트워크 밖으로 나가는 출입구(보통 라우터). 다른 망으로 갈 땐 일단 게이트웨이로 보낸다
- 각 라우터는 라우팅 테이블을 보고 "이 목적지는 저쪽으로" 결정 → 홉을 거듭해 도달
- 이 과정에서 IP는 **경로만 책임**지고, 중간에 패킷이 유실돼도 IP 자체는 재전송하지 않는다 (TCP가 담당)

## 정리

- **IP** = 패킷을 **주소(addressing) + 경로(routing)** 로 목적지까지 보내는 네트워크 계층 프로토콜
- **best-effort** — 도착·순서·중복은 보장 안 함 → 그 신뢰성은 [TCP](TCP.md)가 보완 (TCP/IP)
- **IPv4**(32비트, 약 43억) 고갈 → NAT·CIDR로 연명, 근본 해결은 **IPv6**(128비트)
- **공인 IP**(인터넷 유일) vs **사설 IP**(RFC 1918, 내부망) — 외부로 나갈 땐 **NAT** 변환
- **CIDR**(`/24` 등)로 네트워크 범위 표기 — VPC·보안그룹 설계의 기본
- **TTL**(홉마다 감소, 0이면 폐기), **Protocol**(TCP=6) 등 헤더 필드가 패킷 전달을 제어
