# 방화벽

> 최종 업데이트: 2026-06-19 | Stateful 세션·클라우드 방화벽(보안그룹/NACL) 포함

## 개념

**방화벽(Firewall)** 은 미리 정한 규칙에 따라 오가는 네트워크 트래픽을 검사해 **허용할지 차단할지 결정하는 보안 장치**다. 신뢰하는 내부망과 신뢰할 수 없는 외부망(인터넷) 사이의 **장벽** 역할을 한다.

> 비유: 건물 출입 검문소다. 들어오고 나가는 사람(패킷)을 명단·규칙에 따라 통과시키거나 막는다. 검문 방식이 단순한지(명단만), 한 번 들어온 일행을 기억하는지, 짐 속까지 뒤지는지에 따라 방화벽 종류가 갈린다.

방화벽은 하드웨어 장비·소프트웨어·둘의 조합일 수 있고, 검사 기준은 **IP 주소·포트·프로토콜**부터 애플리케이션 내용까지 다양하다.

## 배경/역사 — 방화벽의 세대 진화

방화벽은 "무엇까지 보고 판단하느냐"가 깊어지며 세대가 올라갔다.

| 세대 | 시기 | 방식 | 한계/발전 |
|------|------|------|----------|
| **1세대 패킷 필터** | 1980년대 말 (DEC) | IP·포트만 보고 패킷별 허용/차단 (**stateless**) | 연결 맥락을 모름 |
| **2세대 Stateful** | 1994 (**Check Point FireWall-1**, Gil Shwed) | **연결 상태를 추적**해 판단 | 현대 방화벽의 표준이 됨 |
| **3세대 응용·프록시** | 1990년대 말 | 애플리케이션 계층까지 대리 검사 | 내부를 숨김 |
| **NGFW** | 2007~ (**Palo Alto Networks**, Nir Zuk) | DPI·IPS·앱 인식을 통합 | 내용물까지 검사 |

핵심 전환점은 **2세대 Stateful**이다. 1세대가 패킷을 하나하나 따로 봤다면, 2세대부터 "이 패킷이 어느 연결에 속하나"를 추적하면서 방화벽이 실용화됐다.

## 방화벽 유형

### 패킷 필터링 (Stateless)

IP 주소·포트·프로토콜 같은 **헤더 정보만** 보고 패킷을 **하나하나 독립적으로** 허용/차단한다.

> 비유: 매 사람마다 명단만 대조하는 검문소. 들어온 사람이 나갈 때도, 그 사람의 응답도 **전부 따로** 검문해야 한다. 그래서 "응답 트래픽(return traffic)"용 규칙을 일일이 만들어야 한다.

- 단순하고 빠르지만 **연결 맥락을 모른다**
- 뒤에 나올 클라우드의 **NACL**이 이 방식이다

### 상태 저장 검사 (Stateful)

패킷을 **하나하나 독립적으로** 보는 게 아니라, **"이 패킷이 어느 연결에 속하나"** 를 추적해 판단한다. 이 연결 추적을 **connection tracking(conntrack)**, 추적 기록을 담는 표를 **세션 테이블(연결 추적 테이블)** 이라 한다. 현대 방화벽·NAT는 거의 다 이 방식이다.

> 비유: 클럽 입장과 같다. **화이트리스트**는 'VIP 명단'(이름 있으면 언제든 입장)이고, **세션 테이블**은 '지금 안에서 대화 중인 일행'이다. 입장은 명단으로 했어도, 들어와 대화 중인 사람을 매번 다시 검문하진 않는다.

#### 트래픽을 통과시키는 두 가지 길

방화벽이 패킷을 통과시키는 경로는 둘이다. **"등록 안 된 IP는 무조건 차단"은 새 연결(NEW)에만** 해당하고, 이미 맺어진 세션의 패킷은 다른 길로 통과한다.

| 경로 | 통과 기준 |
|------|----------|
| **① IP 화이트리스트** | 등록된 IP의 **새 연결**이면 통과 |
| **② Stateful 세션 테이블** | **이미 established된 연결**의 후속 패킷이면 룰과 무관하게 통과 |

이게 없으면 응답 패킷(return traffic)마다 일일이 허용 룰을 만들어야 해서 운영이 불가능하다. 그래서 방화벽은 패킷의 **연결 상태**를 보고 판단한다.

| 연결 상태 | 방화벽 판단 |
|----------|------------|
| **NEW** (새 연결 시작) | 룰(화이트리스트) 검사 → 없으면 **차단** |
| **ESTABLISHED** (맺어진 연결) | 세션 테이블에 있으면 **룰 무관 통과** |
| **RELATED** (기존 연결의 부속 연결) | 통과 (예: FTP 데이터 채널) |
| **INVALID** (추적 안 되는 패킷) | 차단 |

즉 **화이트리스트는 "새 연결을 열 자격"**, **세션 테이블은 "이미 열린 연결의 통행증"** 이다. 둘은 다른 층위다.

#### Idle Timeout — 세션 테이블은 영원하지 않다

세션 테이블은 무한정 유지되지 않는다. **일정 시간 패킷이 안 오가면(idle) 그 세션을 테이블에서 제거**한다(자원 보호). 세션이 제거된 뒤 다시 패킷이 오면, 방화벽은 그 연결을 **모르므로 NEW로 취급** → 화이트리스트에 없으면 차단한다.

> 클럽 비유 연장: 일행 중 한 명이 너무 오래 가만히 있으면, 경비가 "쟤 누구였지?" 하고 **잊어버린다**(idle timeout). 다시 움직이는 순간 명단을 재검문하고, 이름이 없으면 쫓아낸다.

클라우드 환경은 이 타임아웃이 특히 짧아 단골 함정이다.

| 장비 | 유휴 타임아웃(예) |
|------|------------------|
| **AWS NLB** | 기본 350초 |
| NAT Gateway·중간 방화벽 | 분 단위가 흔함 |

**NAT도 본질적으로 같은 세션 테이블을 쓰므로** 동일한 idle timeout 문제를 겪는다.

#### 실무 장애 패턴 — 세션에만 의존할 때

화이트리스트에 IP가 없고 **오직 stateful 세션으로만** 통과하던 연결은, **간헐적(idle)** 통신일 때 끊긴다. 예를 들어 발송 결과(REPORT)가 띄엄띄엄 오는 채널이 그렇다.

```
① 연결 직후 활발히 통신 → 세션 ESTABLISHED, 테이블에 살아있음 → 통과 ✓
② 통신이 간헐적 → idle 구간 발생
③ 방화벽/NAT가 idle timeout으로 세션 제거
④ 이후 패킷 도착 → 세션 없음 → NEW 취급 → IP 화이트리스트에 없음 → 차단 ✗
```

화이트리스트가 있었다면 세션이 죽어도 NEW로 다시 통과됐겠지만, **세션이라는 불안정한 길 하나에만 의존**하다 idle에 끊긴 것이다.

#### 해결 두 갈래

| 방법 | 내용 |
|------|------|
| **① 화이트리스트 등록 (근본)** | 출발지 IP를 방화벽에 등록 → 세션이 죽어도 NEW로 재통과 |
| **② Keepalive·Heartbeat (보완)** | idle가 안 생기게 주기적으로 빈 패킷·핑을 흘려 **세션 테이블을 계속 갱신** |

- ①이 정석이다. 세션에만 의존하는 구조 자체가 불안정하다
- ②는 보완책. **TCP keepalive**, SMPP의 **enquire_link**(핑)가 이 idle 방지용이다. 반드시 **타임아웃(예: 350초)보다 짧은 주기**로 보내야 효과가 있다 → [TCP](통신-프로토콜/TCP.md)

### 프록시 방화벽

방화벽이 **중개자**로서 트래픽을 대신 받고 검사한 뒤 목적지로 전달한다. 내부 시스템을 외부에 직접 노출하지 않아 보안 계층이 하나 더 생긴다.

> 비유: 대리 수령 데스크. 외부인은 데스크하고만 대화하고, 실제 내부 직원·구조는 보이지 않는다.

### 차세대 방화벽 (NGFW)

심층 패킷 검사(DPI), 애플리케이션 수준 필터링, 침입 방지(IPS)를 **통합**한 방화벽이다. 단순히 IP·포트가 아니라 **"어떤 앱의 트래픽이고 내용이 위험한가"** 까지 본다.

> 비유: 명단·일행 확인을 넘어 **짐을 X-ray로 투시**해 내용물까지 검사하는 검문소.

## 방화벽 정책 구성

### 화이트리스트 vs 블랙리스트

| 방식 | 정의 | 성격 |
|------|------|------|
| **화이트리스트** | 허용할 것만 명시, 나머지 전부 차단 | 보수적·안전 (기본 차단) |
| **블랙리스트** | 차단할 것만 명시, 나머지 전부 허용 | 개방적 (알려진 위협만 차단) |

보안이 중요한 망은 **화이트리스트 + 기본 차단(default deny)** 이 원칙이다. "명시적으로 허용한 것 외에는 전부 막는다"가 안전하다.

### 네트워크 영역과 DMZ

방화벽은 망을 **영역(zone)** 으로 나눠 서로 다른 규칙을 적용한다. 대표적으로 **DMZ(완충지대)** 가 있다.

> 비유: 건물의 **로비**. 외부 손님이 바로 사무실(내부망)로 못 들어오고, 일단 로비(DMZ)까지만 들어온다. 외부에 공개해야 하는 웹 서버 등을 DMZ에 두어, 뚫려도 내부망까지 번지지 않게 격리한다.

## 클라우드 방화벽 — 보안그룹 vs NACL

AWS 같은 클라우드에선 방화벽이 **보안 그룹(Security Group)** 과 **NACL(Network ACL)** 두 가지로 나뉜다. 둘의 결정적 차이가 바로 **stateful이냐 stateless냐**라, 앞 개념이 실무에 그대로 꽂힌다.

| 구분 | 보안 그룹 | NACL |
|------|----------|------|
| 상태 추적 | **Stateful** | **Stateless** |
| 적용 단위 | 인스턴스(ENI) | 서브넷 |
| 응답 트래픽 | 인바운드 허용 시 **응답 자동 허용** | 인·아웃바운드 **각각 룰 필요** |
| 규칙 | 허용(allow)만 | 허용·거부(deny) 모두 |

- **보안 그룹(Stateful)**: 인바운드를 허용하면 그에 대한 **응답(아웃바운드)은 세션 추적으로 자동 통과**. 그래서 보통 인바운드만 신경 쓰면 된다
- **NACL(Stateless)**: 상태를 안 보므로 **응답용 임시 포트(ephemeral port) 범위를 아웃바운드에 따로 열어야** 한다. 이걸 빠뜨리면 "요청은 가는데 응답이 막히는" 증상이 난다 → 앞서 본 stateless 패킷 필터의 한계 그대로

> 실무 팁: "분명 보안그룹은 열었는데 통신이 안 된다"면 **NACL의 아웃바운드 ephemeral 포트**를 의심한다. NACL이 stateless라 응답 경로를 안 열어준 경우가 흔하다. 패킷이 실제로 막히는지는 [tcpdump](../../Linux/네트워크/tcpdump.md)로 RST·무응답을 확인한다.
